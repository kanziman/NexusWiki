# ask-thread-history Specification

## Purpose

Ask 대화를 작성자 소유 스레드로 안전하게 보존하고, 완료된 답변의 발급 위키·원문 인용을 새로고침이나 다른 기기에서도 동일하게 복원하도록 사용자 흐름과 격리·신뢰성 계약을 정의한다.

## Requirements

### Requirement: 라우트 복귀 가능한 진행 중 Ask 턴
시스템은 워크스페이스 멤버가 새 Ask 대화에서 첫 질문을 제출하면, 답변 토큰이나 최종 인용을 생성하기 전에 작성자·워크스페이스 소유의 스레드와 `client_turn_id`에 연결된 진행 중 턴을 MUST 생성해야 한다. 시스템은 생성된 스레드 식별자를 같은 Ask 응답의 초기 메타데이터로 반환해야 하며, 기존 SSE 이벤트 순서(`meta`, 0개 이상의 `delta`, `citations`, `done`)는 유지해야 한다. 진행 중 턴은 질문과 생성 중 상태로 조회 가능해야 하고, 최종 답변이 준비되면 같은 논리 턴을 최종 답변·발급 인용·최종 상태로 확정해야 한다.

#### Scenario: 첫 질문 제출 직후 스레드 식별
- **WHEN** 워크스페이스 멤버가 새 Ask 대화에서 유효한 첫 질문을 제출한다
- **THEN** 시스템은 답변 스트리밍 전에 작성자 소유 스레드와 진행 중 턴을 생성하고, 초기 `meta` 이벤트에서 그 스레드 식별자를 반환한다

#### Scenario: 앱 내부 라우트 이동 뒤 진행 중 대화 복귀
- **WHEN** 멤버가 진행 중인 Ask 대화에서 홈 대시보드 등 같은 워크스페이스의 다른 라우트로 이동한 뒤 Ask 진입점으로 돌아온다
- **THEN** 시스템은 같은 브라우저 세션에서 마지막으로 활성화했던 스레드를 열고, 질문과 답변 생성 중 상태 또는 이미 확정된 최종 턴을 보여준다

#### Scenario: 완료 뒤 Ask 진입점 복귀
- **WHEN** 멤버가 Ask 대화에서 벗어난 동안 진행 중 턴이 최종 답변과 인용으로 확정되고 Ask 진입점으로 돌아온다
- **THEN** 시스템은 빈 새 대화 대신 해당 스레드의 최종 답변과 클릭 가능한 위키·원문 인용을 복원한다

#### Scenario: 명시적인 새 대화 시작
- **WHEN** 멤버가 새 대화 동작을 명시적으로 선택한다
- **THEN** 시스템은 이전에 활성화했던 스레드를 자동으로 열지 않고 빈 새 대화 상태를 보여준다

#### Scenario: 진행 중 턴의 최종 확정
- **WHEN** 서버가 진행 중 턴의 최종 답변과 인용을 조립하거나 근거 없음·오류 최종 상태를 결정한다
- **THEN** 시스템은 같은 `(thread_id, client_turn_id)` 논리 턴을 중복 생성하지 않고 최종 상태로 확정한 뒤에만 `done`을 보낸다

### Requirement: 사용자 소유 Ask 스레드 생명주기
시스템은 인증된 워크스페이스 멤버가 자신의 Ask 대화 스레드를 생성하고, 최근 활동순으로 목록 조회하고, 열고, 이름을 변경하고, 삭제할 수 있게 SHALL 제공한다. 새 스레드의 기본 제목은 첫 질문에서 자동으로 만들고, 사용자가 비어 있지 않은 제목으로 변경할 수 있어야 한다.

#### Scenario: 새 대화 시작
- **WHEN** 워크스페이스 멤버가 Ask 화면에서 새 대화를 시작하고 첫 질문을 제출한다
- **THEN** 시스템은 해당 워크스페이스와 작성자에게 속한 스레드를 만들고 첫 질문에서 식별 가능한 기본 제목을 생성한다

#### Scenario: 자신의 대화 목록 조회와 전환
- **WHEN** 작성자가 대화 목록을 열고 저장된 스레드를 선택한다
- **THEN** 시스템은 해당 작성자의 스레드만 최근 활동순으로 보여주고 선택한 스레드의 저장된 턴을 불러온다

#### Scenario: 대화 이름 변경
- **WHEN** 작성자가 자신의 스레드 제목을 비어 있지 않은 값으로 변경한다
- **THEN** 시스템은 변경된 제목을 저장하고 이후 목록 조회에 같은 제목을 반환한다

#### Scenario: 대화 삭제 확인
- **WHEN** 작성자가 삭제 확인을 거쳐 자신의 스레드를 삭제한다
- **THEN** 시스템은 스레드와 그 턴을 더 이상 조회할 수 없게 제거하고 목록에서 다음 대화 또는 새 대화 상태를 보여준다

### Requirement: 완료된 턴의 내구성과 멱등성
시스템은 각 사용자 질문에 클라이언트가 생성한 영문 식별자 `client_turn_id`를 연결하고, 최종 `citations`를 조립한 턴을 at-least-once 방식으로 영속화하되 같은 `(thread_id, client_turn_id)`는 하나의 논리 턴으로 MUST 처리한다. 서버는 요청자 JWT의 `user_client`로 질문과 최종 답변을 내구 저장한 뒤에만 SSE `done`을 보내야 하며, `done`은 해당 완료 턴이 이미 저장되었다는 보장이어야 한다.

#### Scenario: 정상 완료 후 done 발행
- **WHEN** 서버가 질문의 최종 답변 텍스트와 발급 인용을 조립하고 영속화를 성공한다
- **THEN** 서버는 그 뒤에 SSE `done`을 한 번 보내고 클라이언트는 빈 `done` 페이로드를 별도 저장의 소스 오브 트루스로 사용하지 않는다

#### Scenario: 동일 완료 턴 재전달
- **WHEN** 네트워크 재시도나 at-least-once 실행으로 같은 `thread_id`와 `client_turn_id`의 완료 턴이 다시 영속화된다
- **THEN** 시스템은 성공으로 수렴하면서 질문·답변 턴을 중복 생성하지 않는다

#### Scenario: 사용자가 명시적으로 답변 재시도
- **WHEN** 사용자가 같은 질문의 답변 생성을 다시 요청한다
- **THEN** 클라이언트는 새 `client_turn_id`를 사용하고 시스템은 이를 별도의 논리 턴으로 저장한다

#### Scenario: 영속화 실패
- **WHEN** 최종 답변을 조립했지만 완료 턴을 내구 저장하지 못한다
- **THEN** 서버는 저장되지 않은 완료를 뜻하는 SSE `done`을 보내지 않고 재시도 가능한 실패로 처리한다

### Requirement: 복원된 턴의 이중 Citation 재수화
시스템은 완료된 답변의 최종 `text`와 서버가 실제 발급한 `resolved` 항목의 `alias`, `kind`, `id`를 함께 MUST 저장하고 반환한다. 복원 경로는 이 정보를 사용하여 `kind`가 `wiki`인 위키 마커와 `kind`가 `source`인 원문 마커를 모두 클릭 가능한 상태로 재수화해야 하며, 발급된 마커를 비활성 placeholder로 표시해서는 안 된다.

#### Scenario: 위키와 원문 인용이 있는 답변 복원
- **WHEN** 사용자가 발급된 위키 인용과 원문 인용을 모두 포함한 저장 스레드를 다시 연다
- **THEN** 시스템은 저장된 `text`와 `resolved`를 결합하여 두 종류의 마커를 모두 클릭 가능하게 렌더하고 각각 기존 위키·원문 인용 탐색 경로로 연결한다

#### Scenario: 발급되지 않은 앵커가 포함된 저장 텍스트
- **WHEN** 저장된 답변 텍스트의 앵커가 `resolved` 발급 목록에 없다
- **THEN** 시스템은 그 앵커를 클릭 가능한 인용으로 승격하지 않고 최종 답변의 인용 무결성 규칙을 유지한다

#### Scenario: 근거 없음 또는 오류 턴 복원
- **WHEN** 저장된 턴이 `no-evidence` 또는 `error` 최종 상태로 끝났다
- **THEN** 시스템은 빈 인용을 placeholder로 만들지 않고 해당 최종 안내 상태와 재시도 동작을 복원한다

#### Scenario: 연결 끊김 상태
- **WHEN** 클라이언트가 최종 인용과 `done` 전에 연결 끊김을 감지한다
- **THEN** 시스템은 클라이언트 로컬 `dropped` 상태를 완료 턴으로 영속화하지 않는다

### Requirement: 작성자와 워크스페이스를 함께 강제하는 RLS
시스템은 모든 Ask 스레드와 턴에 RLS를 적용하고, 인증 사용자가 현재 워크스페이스 멤버이면서 행의 작성자일 때만 접근을 MUST 허용한다. 같은 워크스페이스의 다른 멤버에게도 스레드를 노출하지 않아야 하고, `anon` 역할에는 허용 정책을 제공하지 않아야 한다.

#### Scenario: 작성자인 현재 멤버의 접근
- **WHEN** 인증 사용자가 현재 멤버인 워크스페이스 안에서 자신이 작성한 스레드를 조회하거나 변경한다
- **THEN** RLS는 요청자 신원과 워크스페이스 멤버십을 모두 확인하여 접근을 허용한다

#### Scenario: 같은 워크스페이스의 다른 작성자
- **WHEN** 인증 사용자가 같은 워크스페이스의 다른 사용자가 작성한 스레드를 목록 조회하거나 직접 식별자로 접근한다
- **THEN** RLS는 해당 스레드를 노출하거나 읽기·변경하도록 허용하지 않는다

#### Scenario: 멤버십을 잃은 작성자
- **WHEN** 스레드 작성자가 해당 워크스페이스의 현재 멤버가 아닌 상태로 자신의 이전 스레드에 접근한다
- **THEN** RLS는 작성자 일치만으로 접근을 허용하지 않는다

#### Scenario: 익명 접근
- **WHEN** `anon` 역할이 Ask 스레드 또는 턴을 조회하거나 변경한다
- **THEN** RLS는 모든 접근을 거부한다

#### Scenario: USING 정책이 쓰기를 0행으로 만든 경우
- **WHEN** 작성자 또는 멤버십 조건을 만족하지 않는 UPDATE나 DELETE가 RLS `USING` 정책 때문에 영향 행 수 0을 반환한다
- **THEN** API는 이를 성공으로 처리하지 않고 HTTP 403으로 응답한다

### Requirement: 사용자 요청의 JWT 데이터 경로
시스템은 Ask 스레드 목록·조회·생성·이름 변경·삭제와 완료 턴 영속화를 포함한 모든 사용자 요청 경로에서 요청자 JWT로 구성한 `user_client`를 MUST 사용하고, RLS를 우회하는 `service_role`을 MUST NOT 사용한다.

#### Scenario: 스레드 사용자 요청 처리
- **WHEN** 인증 사용자가 Ask 스레드 API를 호출하거나 Ask 답변이 완료되어 턴을 저장한다
- **THEN** 모든 데이터 접근은 같은 요청자의 JWT 신원을 전달하는 `user_client`로 실행되고 RLS 평가를 받는다

#### Scenario: 우회 자격 증명 방지
- **WHEN** 사용자 시작 Ask 스레드 경로의 데이터 클라이언트를 검사한다
- **THEN** `service_role` 또는 그와 동등한 RLS 우회 자격 증명이 사용되지 않는다

### Requirement: 스레드 전환 중인 Ask 요청의 지속
시스템은 사용자가 답변 스트리밍 중 다른 스레드나 새 대화로 전환하더라도 이미 시작한 Ask 요청을 취소하지 않고 완료와 영속화를 MUST 계속해야 한다. 사용자가 원래 스레드로 돌아오면 서버에 저장된 실제 최종 상태를 기준으로 턴을 복원해야 한다.

#### Scenario: 스트리밍 중 다른 스레드로 이동
- **WHEN** 사용자가 답변이 스트리밍 중인 스레드에서 다른 스레드로 전환한다
- **THEN** 기존 Ask 요청은 백그라운드에서 완료와 영속화를 계속하고 새 스레드의 대화가 표시된다

#### Scenario: 완료 후 원래 스레드로 복귀
- **WHEN** 사용자가 백그라운드 요청이 `done`까지 완료된 원래 스레드로 돌아온다
- **THEN** 시스템은 서버에 저장된 최종 턴과 클릭 가능한 이중 인용을 복원한다

### Requirement: 기존 grounded Ask 의미 보존
스레드 이력은 저장과 표시를 위한 기능이어야 하며, 이전 턴을 후속 질문의 LLM 프롬프트 문맥으로 자동 재주입해서는 안 된다. 기존 SSE 이벤트 순서 `meta`, `delta`, `citations`, `done`과 단건 grounded 답변 의미는 MUST 유지한다.

#### Scenario: 저장 스레드에서 후속 질문
- **WHEN** 사용자가 이전 턴이 있는 저장 스레드에서 새 질문을 제출한다
- **THEN** 시스템은 이전 대화 내용을 LLM 문맥에 자동 추가하지 않고 새 질문을 기존 단건 grounded Ask 계약으로 처리한다

#### Scenario: SSE 호환성
- **WHEN** 스레드 식별자가 포함된 Ask 요청이 정상 완료된다
- **THEN** 클라이언트는 `meta`, 0개 이상의 `delta`, `citations`, `done` 순서의 기존 이벤트 계약을 계속 받는다

### Requirement: 저장소 작성 규약
이 변경의 문서와 코드 주석은 한국어로 작성하고, 파일명·API 필드·타입·함수·데이터베이스 객체 같은 식별자는 영문 또는 ASCII로 MUST 작성한다. 모든 SQL 키워드와 식별자는 소문자로 작성해야 한다.

#### Scenario: 계획 문서와 구현 산출물 검토
- **WHEN** 이 변경의 OpenSpec 문서, 코드 주석, 식별자, 마이그레이션 SQL을 검토한다
- **THEN** 설명 문구는 한국어이고 식별자는 영문 또는 ASCII이며 SQL은 키워드와 식별자를 포함해 소문자다
