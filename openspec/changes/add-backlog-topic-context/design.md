## 표기와 발췌를 서버가 한 번에 만든다

목록 로드 시점에 Server Component가 영향받는 위키 본문을 읽어 **주제별 표기와 발췌를 모두 계산해** props로 내려보낸다. 상세 패널은 그 props만 소비하는 클라이언트 상태다.

Gate 1의 결정이 이 선택을 사실상 강제한다. 모든 행의 라벨이 인용 문서 본문 스캔에서 나오므로 **본문 읽기는 어느 안을 골라도 목록 로드에서 피할 수 없다.** 이미 메모리에 올라온 본문에서 발췌 문자열을 만드는 비용은 0에 가깝다 — 미루는 쪽이 오히려 비싸다.

기각한 두 안:

- **URL 파라미터(`?topic=`) + 서버 재렌더.** 딥링크를 주지만 행을 열 때마다 전체 집계(모든 미해결 링크 + 인용 문서 + 본문 스캔)를 다시 돌린다. 패널 하나 여는 대가로 목록 전체를 재계산한다.
- **읽기용 Server Action 온디맨드.** 이미 읽었던 본문을 다시 읽는다. 게다가 이 저장소의 유일한 server action(`app/onboarding-actions.ts`)은 mutation이라, 읽기 경로의 선례를 새로 만드는 값에 비해 얻는 것이 없다.

⚠️ **`ContentViewer`·`GraphLensFilter`의 "URL이 상태" 관용구를 여기에 그대로 쓸 수 없다.** 그 관용구의 실체는 URL 파라미터 + **클라이언트 fetch**인데, 그러면 `wiki_pages.content`가 클라이언트로 내려간다. `backlog-management-prd.md` §4.3이 금지하는 바로 그 동작이다. 관용구를 따르지 않은 것이 실수가 아니라 이 제약 때문이라는 사실을 여기 남긴다.

## 인용 문서 조회를 영향받는 문서로 제한한다

현재 `backlog/page.tsx`는 워크스페이스의 **모든** `wiki_pages`를 읽는다(`id,slug,title`). 여기에 `content`를 그냥 더하면 워크스페이스 전체 본문을 매 요청마다 읽게 된다.

미해결 링크의 `from_wiki_id`에 실제로 등장하는 id 집합으로 `.in()` 제한한다. 그러면 읽는 양이 **결손이 있는 문서 수**로 묶인다 — 백로그가 비어 있으면 본문을 한 줄도 읽지 않는다.

## 표기 결정 규칙은 결정적이어야 한다

인용 문서들에서 모은 `[[...]]` 표기 중 **최빈값**을 쓰고, 동수면 `backlog-management-prd.md` §4.1의 정렬(위키 제목 오름차순)에서 앞선 문서의 표기를 따른다. 하나도 찾지 못하면 `target_slug` 역변환으로 폴백하고, 원본 slug는 보조 줄에 계속 병기한다.

⚠️ tie-break를 정하지 않으면 라벨이 렌더마다 바뀔 수 있다. 조회 순서는 보장되지 않고, 그렇게 흔들리는 화면은 **테스트를 통과하면서** 사용자에게만 깨져 보인다.

발췌의 세부 규칙도 같은 이유로 못박는다:

- 한 문서에 같은 링크가 여러 번 나오면 **첫 등장**만 쓴다.
- 링크가 등장한 지점 앞뒤를 잘라 한 조각으로 만들고, 잘린 쪽에는 말줄임을 붙인다.
- 발췌 안에 다른 `[[...]]`가 섞여 있으면 **전부 평문으로 펼친다.** 브래킷 노출 금지는 공개 표면만의 규칙이 아니다 — 내부 화면에서도 내부 마크업을 그대로 보여주지 않는다.

## 격리 경계는 그대로다

`page.tsx`는 지금처럼 요청자 세션(`lib/supabase/server`의 `createClient`)으로 조회한다. `service_client`를 쓰지 않는다 — `wiki_pages`·`wiki_links` 양쪽의 SELECT 정책이 그대로 경계를 강제한다. 이 change는 **읽는 컬럼을 하나 늘릴 뿐 조회 주체를 바꾸지 않는다.**

`wiki_links`에는 여전히 쓰기 경로가 없다. 백로그는 `link_sync`가 소유하는 파생 상태이고 이 화면은 읽기 전용이다.

## 패널은 기존 모달 관용구를 쓴다

`SourcesList`의 업로드 모달과 같은 Radix Dialog를 쓰고, 조판은 `nexuswiki-design-system.css` 섹션 17(작성 대기 백로그)에 얹는다. 새 오버레이 프리미티브를 만들지 않는다.

⚠️ 섹션 15의 `.drawer`를 재사용하지 않는다. 그쪽은 `left:264px; right:280px`로 앱 셸 사이드바와 리더 목차 폭을 전제한 하단 드로어라, 백로그 화면에서는 좌표가 맞지 않는다.

## Non-Goals

- **딥링크 URL 상태.** 패널은 URL을 갖지 않는다. 필요해지면 발췌 생산이 서버에 남아 있으므로 스펙 계약을 바꾸지 않고 별도 change로 얹을 수 있다.
- **스키마 변경.** `origin`·`target_title` 컬럼을 만들지 않는다(PRD §2.1·§6-2(b)). 표기는 본문에서 복원하지 저장하지 않는다.
- **발췌 저장·캐싱.** 조회 시점에 만든다. 본문이 바뀌면 자동으로 최신이 되는 것이 이 방식의 이점이다.
- **백로그 쓰기 액션.** 수동 등록·보류·무시·담당자 지정을 넣지 않는다(PRD §2.1·§3.4).
- **해결 완료 목록.** 해결된 링크는 백로그에서 빠질 뿐이고 해결 시각을 기록하지 않는다(PRD §3.4).
- **마크다운 렌더링 확장.** 발췌는 평문 조각이다. 위키 리더의 본문 조판을 패널로 가져오지 않는다.
- **"지식 완성 커버리지 %".** 정의가 없다(PRD §6-1). 상단 통계는 2종을 유지한다.
