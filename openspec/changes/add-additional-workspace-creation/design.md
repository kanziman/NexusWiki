## Context

`/` 는 `add-google-oauth-onboarding`이 정의한 진입 분기(0개 → 온보딩, 1개 → 리다이렉트, 2개 이상 → 선택 화면)를 그대로 소유한다. 이 change는 그 분기를 건드리지 않고, 소속이 있는 사용자가 생성 폼에 도달할 별도 경로만 추가한다. 재사용 가능한 이름 입력 폼(`WorkspaceOnboarding` 컴포넌트)과 생성 서버 액션(`createPersonalWorkspace`)은 `add-google-oauth-onboarding`이 이미 구현했다 — 이 change는 그 구성요소를 새 진입 조건에서 재사용한다. 동기는 proposal.md 참조.

## Goals / Non-Goals

**Goals:**
- 소속 개수와 무관하게 생성 폼에 도달 가능한 라우트 제공
- 무제한 셀프서브 생성 남용 방지

**Non-Goals:**
- `/` 의 진입 분기 로직 변경 (`add-google-oauth-onboarding` 소관, 유지)
- 팀 워크스페이스(kind='team') 생성 흐름 — 셀프서브는 `personal`만 만든다(기존 동작 유지)
- 상한 값을 사용자별로 조정 가능하게 만드는 것 — 지금은 고정 상수

## Decisions

**라우트를 `/w/new`로 둔다 (쿼리 파라미터 방식 대신).**
`/w/[workspaceId]`와 같은 부모 아래 정적 세그먼트로 두면 Next.js App Router가 정적 세그먼트를 동적 세그먼트보다 우선 매칭해 라우트 충돌 없이 별도 페이지로 렌더링된다. `/?new=1` 같은 쿼리 파라미터 방식도 검토했으나, `/`의 리다이렉트 분기(1개 → 즉시 `redirect()`)가 쿼리 파라미터를 무시하고 먼저 실행되므로 그 분기를 함께 수정해야 했다 — Non-Goal(`/` 로직 불변)과 충돌해 기각.

**인증 게이트를 이 라우트에서 새로 만들지 않는다.**
`middleware.ts`의 matcher가 이미 `/w/:path*`를 포함해 `/w/new`도 커버한다. 별도 게이트를 추가하면 로그인 상태 판정이 두 곳(D-02 boundary 위반)에 생긴다.

**상한 판정을 서버 액션(`createPersonalWorkspace`)에 둔다 (클라이언트/페이지 표시 로직이 아니라).**
워크스페이스 스위처의 링크 숨김과 `/w/new` 페이지의 안내 문구는 둘 다 표시용이다 — 실제 요청은 사용자가 UI를 우회해 서버 액션을 직접 호출할 수 있으므로, 삽입 직전 서버 액션에서 RLS 스코프 개수를 다시 세는 것만이 정본이다. `budget` 화면이 이미 쓰는 "표시와 집행 지점을 분리한다" 원칙(workspace-settings PRD §3.3.1)과 같은 패턴이다.

**대안으로 검토했으나 기각한 것: DB 트리거로 개수 제한.**
`workspaces` INSERT 트리거로 owner당 개수를 강제하는 방법도 가능하지만, 이 상한은 테넌트 격리 경계가 아니라 자기 자신 리소스에 대한 소프트 UX 가드레일이다(tenant-isolation-reviewer PR #43 리뷰 판정). 마이그레이션까지 동원할 근거가 부족해 애플리케이션 레벨 검사로 충분하다고 판단했다.

## Risks / Trade-offs

- **[Risk] 동시 제출 레이스** — 두 탭에서 동시에 제출하면 상한을 1개 넘길 수 있다(카운트 조회와 INSERT 사이 원자성 없음). → **Mitigation**: 자기 자신 리소스에 대한 소프트 가드레일이라 허용 가능한 트레이드오프로 수용한다. 테넌트 경계를 침해하지 않으므로 즉시 수정하지 않는다 — 재발 시 DB 트리거로 상향할 근거가 된다.
- **[Risk] 상한 값(3)이 하드코딩** — 향후 요금제별로 달라지면 재작업이 필요하다. → **Mitigation**: 지금은 단일 상수로 충분하다고 판단(Non-Goal). 요금제 도입 시 별도 change에서 다룬다.
