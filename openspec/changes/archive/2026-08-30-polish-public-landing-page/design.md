## Context

동기와 사용자 계약은 [proposal.md](proposal.md)와 `public-marketing-landing` delta spec을 따른다. 현재 공개 랜딩은 `PublicLandingPage.tsx` 한 파일에 정적 콘텐츠, 세 쇼케이스 상태, FAQ 상태와 모든 SVG 마크업이 함께 들어 있다. 루트 서버 컴포넌트와 미들웨어의 인증 분기는 이미 기존 테스트를 통과하므로 이 경계를 보존해야 한다.

## Goals / Non-Goals

**Goals:**

- 상위 공개 랜딩이 쇼케이스·FAQ·모바일 메뉴 상태를 소유하는 현재 단방향 흐름을 유지한다.
- 헤더, 라이브 쇼케이스, FAQ를 독립 표시 컴포넌트로 분리해 반응형·접근성 계약을 좁게 테스트한다.
- 기존 v2 토큰과 청록 accent, 편집형 정보 밀도, 실제 제품 화면을 닮은 쇼케이스를 보존한다.
- 확인 가능한 제품 계약만 남기고 절대적 처리 시간·용량·격리 수치·모델 학습 주장을 제거한다.

**Non-Goals:**

- 랜딩의 전체 정보 구조나 시각 방향을 새로 설계하지 않는다.
- CMS, 분석 이벤트, 가격표, 결제, 외부 콘텐츠 API를 추가하지 않는다.
- 인증 사용자 루트 진입, 로그인 화면, 공개 위키 뷰어를 변경하지 않는다.
- 복잡한 애니메이션 라이브러리나 새 UI 의존성을 추가하지 않는다.

## Decisions

### 1. 상위 상태 + 세 개의 표시 컴포넌트로 분리한다

`PublicLandingPage`는 `currentWsIdx`, `currentScenarioIdx`, `openFaq`, `mobileMenuOpen`을 소유한다. `PublicLandingHeader`, `PublicLandingShowcase`, `PublicLandingFaq`는 값과 이벤트 콜백을 props로 받아 렌더링한다. 쇼케이스 콘텐츠 타입과 정적 시나리오는 별도 콘텐츠 모듈로 옮겨 컴포넌트 테스트가 동일 데이터를 재사용하게 한다.

선택한 이유는 API·데이터 구조를 바꾸지 않으면서 1,095줄 파일의 상태와 표시 책임을 분리하고, 각 접근성 계약을 직접 테스트할 수 있기 때문이다.

- 대안 A, 단일 파일 직접 보완: 변경량은 작지만 상태·마크업·콘텐츠 결합과 테스트 어려움이 남는다.
- 대안 C, JSON 섹션 스키마 렌더러: 콘텐츠 교체에는 유리하지만 현재 규모에서 타입과 디버깅 복잡도를 늘린다.

### 2. 모바일 헤더는 토글 메뉴로 동일한 탐색 경로를 제공한다

데스크톱 링크는 기존 인라인 내비게이션을 유지한다. 모바일에서는 브랜드 잠금장치의 보조 배지를 숨기고, 로그인·시작 CTA와 충돌하지 않는 메뉴 버튼을 제공한다. 메뉴는 `aria-expanded`, `aria-controls`를 노출하고 섹션 링크 선택 뒤 닫힌다. 로그인과 주요 시작 CTA는 메뉴 내부에서도 제공한다.

단순히 데스크톱 내비게이션을 숨기는 대안은 모바일 사용자가 쇼케이스·동작 원리·활용 사례·FAQ로 이동할 수 없으므로 제외한다.

### 3. 쇼케이스 선택 상태와 FAQ 관계를 명시한다

워크스페이스 선택은 단일 선택 `tablist`/`tab`으로, 추천 질문은 `aria-pressed` 버튼 그룹으로 표현한다. 결과 영역은 `aria-live="polite"`로 갱신을 알린다. FAQ 버튼은 고유한 질문·패널 ID, `aria-expanded`, `aria-controls`, `aria-labelledby`를 연결하고 닫힌 패널은 DOM에서 제거한다.

CSS 색상만으로 현재 상태를 표현하는 방식은 키보드·스크린리더 사용자가 선택을 확인할 수 없으므로 사용하지 않는다.

### 4. 기존 토큰을 유지하면서 장식 패턴과 문구만 정리한다

새 색상·폰트·그림자 토큰은 만들지 않는다. 질문과 근거 블록의 두꺼운 한쪽 테두리는 전체 경계·부드러운 배경·선행 아이콘으로 바꾸고, 반복되는 영문 eyebrow는 정보 계층상 필요한 곳만 남긴다. 실제 순서인 3단계의 번호는 유지한다. pulse와 hover 이동에는 `motion-reduce` 대체를 적용한다.

“1초”, “30초”, “100%”, “수백 편”, “RLS 37개”, “물리 격리”, “외부 모델 학습에 절대 사용되지 않음”처럼 이 저장소의 실행 계약으로 입증되지 않은 표현은 조건 없는 보장에서 제거한다. 대신 소스 자동 컴파일, 발급된 원문·위키 인용, 4채널 검색, 요청자 JWT와 RLS에 의한 워크스페이스 격리처럼 코드와 스펙으로 확인되는 표현을 사용한다.

## Risks / Trade-offs

- [Risk] 컴포넌트 분리 중 기존 쇼케이스 상태 전환이 달라질 수 있다. → 기존 시나리오 데이터를 그대로 옮기고 워크스페이스·추천 질문 전환 테스트를 먼저 고정한다.
- [Risk] 모바일 메뉴가 sticky header 아래에서 콘텐츠를 가리거나 포커스를 잃을 수 있다. → 헤더 내부의 정상 문서 흐름 패널로 렌더하고 링크 선택 시 닫는다.
- [Risk] 마케팅 문구를 보수적으로 바꾸면 전환 메시지가 약해질 수 있다. → 제품의 차별점인 “원문과 위키 양쪽을 함께 인용”을 히어로·쇼케이스·최종 CTA에서 반복해 구체성을 유지한다.
- [Risk] 미추적 초안 파일을 분리하면서 다른 세션의 작업을 잃을 수 있다. → 기존 정적 콘텐츠와 시나리오를 보존하고, 관련 파일만 `apply_patch`로 수정하며 무관한 변경을 스테이징하지 않는다.

## Migration Plan

데이터 마이그레이션은 없다. 공개 홈 컴포넌트와 테스트를 함께 배포하며, 문제가 생기면 새 표시 컴포넌트를 제거하고 `PublicLandingPage`의 이전 단일 파일 렌더링으로 되돌릴 수 있다. 인증 분기와 보호 경로 미들웨어는 동일하게 유지한다.
