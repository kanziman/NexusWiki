## Context

동기는 `proposal.md`를 본다. `fuse_ranked_hits`는 채널별 근거를 돌며 `canonical_id`(위키는 `wiki:<페이지 id>`, 원문은 `source:<청크 id>`)마다 `weight / (rrf_k + rank)`를 더한다. 같은 채널에서 같은 `canonical_id`가 다시 나오면 그 채널 몫에 **더한다**. `wiki_vector`는 페이지의 임베딩 청크를 여러 개 돌려주므로 청크가 많은 페이지가 반복만으로 점수를 얻는다. 원문은 청크가 곧 단위라 이런 반복이 없다.

정책 변경 절차는 `docs/ops/retrieval-policy-change-log.md`가 정본이다: 값 하나만 바꾸고 `POLICY_VERSION`을 올리며, 같은 핀으로 전후 공식 벤치마크 기록(append-only)을 남기고 comparator로 비교한 뒤 변경자가 아닌 사람이 서명한다. 공식 벤치마크(`scripts/benchmark_retrieval.py`)의 비교기는 지금 순서 모드(`compare-order-records`)와 그래프(`compare-graph-records`)만 지원한다.

## Goals / Non-Goals

**Goals:**
- 같은 채널에서 한 근거는 한 번만 기여하게 해 위키의 반복 이득을 없앤다.
- 절차 계약대로 정책 값 하나 변경, 버전 상승, 전후 기록, 비교기, 사람 승인으로 진행한다.
- 공식 벤치마크 외에 재생 검색 평가와 성적표 재생으로 답변 품질 회귀를 함께 확인한다.

**Non-Goals:**
- 어휘 채널 질의 조합(#195 A), 임베딩 실패 표시(#195 C).
- 채널 가중치나 `rrf_k` 조정. 바꾸는 값은 하나다.
- 위키 기여 분리 실험(원문만 · 위키만 · 둘 다). 이 수정 뒤의 별도 작업이다.

## Decisions

**1. 같은 채널 안에서는 최고 순위 한 번만 쓴다(`best_rank`).**
표준 RRF의 정의다. 대안으로 "같은 채널 기여의 최댓값"과 "첫 등장만"이 있으나, 채널 결과가 순위순이면 셋은 같다. 순위가 정렬되지 않은 입력에도 같은 결과를 내도록 **최소 순위**를 명시적으로 고른다. 채널 간 합산은 그대로다(여러 채널이 찾은 근거가 앞서는 것은 RRF의 의도).

**2. 융합 방식을 정책 필드 `same_channel_aggregation`(`"sum"` | `"best_rank"`)로 둔다.**
코드에 숨기면 기록이 어떤 규칙으로 정렬됐는지 알 수 없고, 절차의 "정책 값 하나 변경"을 기록으로 증명할 수 없다. 기본값은 `best_rank`, 버전은 `hybrid-rrf-v2`. `policy_content`에 이 필드를 넣는다. 이전 기록(v1)의 `policy_content`에는 필드가 없으므로 비교기는 **없음을 `sum`으로 해석**한다.

**3. 비교기 `compare-fusion-records`를 추가한다(fail-closed).**
`compare-graph-records`와 같은 모양이다. 핀(코퍼스 · 골든 · 매니페스트 · 생성기 · 워크스페이스 · 모델 · DB · 반복 횟수)이 같아야 하고, 두 기록의 `policy_content` 차이가 `same_channel_aggregation`과 `version` 뿐이어야 통과한다. 다른 필드가 다르면 거부한다.

**4. 공식 벤치마크는 같은 커밋에서 융합 방식만 바꿔 두 팔을 돌리고, 재생 측정은 코드 두 벌로 한다.**
구현 중 확인한 사실: 공식 벤치마크 비교기의 핀(`_pins`)에 `git_sha`가 들어 있다. 코드 두 벌로 돌리면 비교기가 핀 불일치로 거부한다. 그래서 공식 벤치마크는 그래프 비교의 기존 관례처럼 **같은 커밋에서 `--fusion sum`과 `--fusion best_rank`** 로 두 팔을 돌린다. `sum` 팔은 정책 버전을 `hybrid-rrf-v1`로 기록하고 v1과 같은 계산을 한다(`test_sum_policy_reproduces_v1_behaviour`가 고정). 재생 검색 평가와 성적표는 API를 거치므로 before를 `main` worktree 코드로, after를 이 브랜치 코드로 돈다. 이쪽에는 핀 비교기가 없다.

**5. 실행 환경을 분리한다.**
- 공식 벤치마크: `--db-container`가 기본 공유 544xx 스택(`supabase_db_NexusWiki`)을 가리킨다. 다른 세션과 겹치지 않게 실행 전 그 스택의 사용 여부를 확인하고, 전후 두 실행을 같은 스택 · 같은 적재 결과(`--reuse-loaded-workspace`가 허용하면)로 돈다. 로컬 Docker 지연은 운영 근거로 쓰지 않는다(절차 계약).
- 재생 검색 평가와 성적표: 546xx 재생 스택 한 벌에 문서를 **한 번만** 수집하고, 그 위에서 before 코드와 after 코드로 각각 돈다. 재수집마다 위키가 달라지므로(PR #226에서 확인) 수집을 공유해야 비교가 된다. 재생 서버 스크립트(`ask_replay_serve.sh <코드 루트>`)가 코드 루트를 받으므로 worktree를 넘긴다. 워커 포트 8081이 고정이라 한 번에 한 벌만 띄운다.

**6. 재생 검색 기록에 근거별 채널 기여를 남긴다.**
`ranked`의 각 항목에 응답의 `channels`와 `contributions`를 그대로 담는다. 수정 전 기록에서 위키 1위의 `wiki_vector` 기여가 단일 순위 몫(`1/(60+r)`)보다 큰지로 합산을 직접 보인다. 근거 본문은 담지 않는다.

**7. 성공 기준은 "숫자를 보기 전에" 정한다.**
- 검색: 재생 평가에서 원문 근거가 상위 6 안에 들어오는 질문이 늘어야 한다(방향 확인). 공식 벤치마크 `strict_query_pass_rate`와 `recall_at_k`는 떨어지지 않아야 한다.
- 답변: 성적표 재생의 위조 앵커 0건 유지, 통과 문항이 before보다 줄지 않는다(답변 변동이 있어 한 문항 차이는 잡음으로 읽고, 줄면 그 문항의 답을 연다).
- 하나라도 어기면 채택하지 않고 기록만 남긴다(절차: 채택하지 않은 실험도 남긴다).

## Risks / Trade-offs

- **[위키 근거가 덜 잡혀 이중 인용이 줄 수 있음]** → Ask는 `select_dual_evidence`로 위키와 원문을 쿼터만큼 따로 고르므로 영향이 작을 것으로 보지만, 성적표 재생으로 확인한다.
- **[공식 벤치마크가 무겁고 공유 스택을 씀]** 5만 벡터 적재와 반복 3회 → 실행 전 소요 시간과 스택 사용 여부를 사용자에게 알리고 진행한다.
- **[표본이 작음]** 재생 29문항 · 골든 36문항 → 방향과 회귀 여부를 보고, 작은 차이로 개선을 주장하지 않는다.
- **[이전 기록의 해석]** v1 기록에 융합 필드가 없다 → 없음을 `sum`으로 해석하는 규칙을 비교기 코드와 테스트로 고정한다.
- **[독립 리뷰어 서명은 사람만 할 수 있음]** → 구현 완료 후 사용자 서명 전에는 채택 상태를 "승인 대기"로 둔다.

## Migration Plan

DB 변경 없음. 배포는 코드 배포만이며, 문제가 있으면 정책 기본값을 `sum`으로 되돌리고 버전을 다시 올려 롤백한다(절차상 롤백도 변경 이력에 남긴다).

## 리뷰 후속 결정

스펙 준수 r1에서 검색 응답이 버전만 보고해 융합 규칙 식별 시나리오를 충족하지 못함을 확인했다. 검색 응답의 기존 `meta`에 `same_channel_aggregation`을 추가해 정책 버전과 규칙을 함께 보고한다. 응답의 근거·순위·컨텍스트는 바뀌지 않는다. 기본 정책과 이전 합산 정책을 API 서비스 테스트로 대조하며, 답변 생성 입력이 동일하므로 유료 재생은 반복하지 않는다.
