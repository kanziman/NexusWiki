## Context

`ask_messages`는 현재 최종 상태만 허용하고, `persist_ask_turn`이 답변·인용 조립 뒤에 스레드와 메시지를 함께 만든다. 따라서 첫 Ask 요청은 완료 전까지 서버에서 식별할 스레드가 없고, 워크스페이스 셸의 Ask 링크는 항상 쿼리 없는 경로로 이동한다. 동기와 사용자 계약은 [proposal.md](proposal.md)와 `ask-thread-history` delta spec을 따른다.

## Goals / Non-Goals

**Goals:**

- 첫 Ask 제출을 같은 요청자 JWT의 트랜잭션으로 즉시 식별 가능한 스레드·진행 중 메시지로 만든다.
- 기존 최종 턴 행을 갱신해 스트리밍·최종화 사이에 논리 턴이 중복되지 않게 한다.
- 같은 브라우저 세션에서 워크스페이스를 벗어났다가 Ask 진입점을 누르면 마지막 활성 스레드를 다시 연다.
- 기존 `meta`, `delta`, `citations`, `done` SSE 순서와 완료 뒤 `done` 보장을 유지한다.

**Non-Goals:**

- 브라우저 새로고침·탭 닫힘·네트워크 단절 뒤 생성 작업을 독립 백그라운드 작업으로 계속 실행하지 않는다.
- 다른 브라우저·기기에서 마지막 활성 Ask 스레드를 자동 선택하지 않는다.
- 이전 턴을 후속 질문의 LLM 문맥에 추가하지 않는다.

## Decisions

### 1. 첫 SSE `meta` 전에 진행 중 턴을 생성한다

`0019_ask_streaming_turns.sql`은 `ask_messages.status`에 `streaming`을 추가하고, 첫 질문 또는 기존 스레드의 후속 질문을 멱등하게 만드는 `start_ask_turn` RPC를 둔다. 이 RPC는 새 스레드가 필요하면 제목을 첫 질문에서 만들고, `(workspace_id, client_turn_id)`의 고유성으로 같은 재시도를 기존 스레드·메시지로 수렴시킨다.

Ask 라우터는 스트리밍 응답을 열기 전에 요청자 JWT의 `UserDb`로 이 RPC를 호출한다. 성공하면 응답 헤더 `X-Ask-Thread-Id`로 스레드 ID를 즉시 노출하고, 서비스의 첫 `meta` 이벤트에도 같은 ID를 넣는다. 헤더는 기존 SSE 이벤트 순서를 바꾸지 않으면서 브라우저가 검색 완료를 기다리지 않고 활성 스레드를 기록하게 하고, `meta`는 스트림 계약의 식별자 정본이자 하위 호환 경로로 남는다. 초기 생성 실패는 200 SSE가 이미 열린 뒤에 숨기지 않고 기존 API 오류 처리로 반환한다.

`persist_ask_turn`은 `finalize_ask_turn`으로 대체한다. 이 RPC는 처음 생성한 같은 메시지를 `resolved`, `no-evidence`, 또는 `error`로 확정하고 답변·인용을 기록한다. `streaming` 행을 대상으로만 갱신하되, 이미 같은 최종 상태로 확정된 재시도는 같은 행을 돌려 멱등성을 유지한다. 함수는 `security invoker`로 실행하고, 새 메시지 갱신 정책도 작성자·현재 멤버십을 검사한다.

**대안: 최종 단계까지 기존 insert만 유지** — 진행 중 상태를 조회할 수 없어서 라우트 복귀 요구사항을 만족하지 못한다.

**대안: 별도 pending 테이블을 만든 뒤 최종 행으로 복사** — 최종화 시 두 테이블의 이동·정리와 조회 병합이 필요해 멱등성·복구 경로가 불필요하게 복잡해진다.

### 2. 마지막 활성 스레드는 브라우저 세션에 워크스페이스별로 저장한다

Ask 컴포넌트는 응답 헤더의 스레드 ID를 우선 사용하고 `meta.thread_id`를 대체 경로로 받아 URL을 `?thread=<id>`로 정규화한다. 동시에 워크스페이스별 세션 저장소 키에 ID를 기록한다. 워크스페이스 셸의 LNB Ask 링크와 상단 Ask 버튼은 이 값을 읽어 같은 스레드 URL로 이동한다. 값이 없거나 검증되지 않은 값이면 기존 쿼리 없는 Ask 경로를 유지한다.

명시적 새 대화 동작은 해당 세션 값을 지운 뒤 쿼리 없는 Ask 경로로 이동한다. 스레드 상세 조회가 403 또는 부재로 끝나면 저장한 값을 지워 다음 진입에서 삭제·권한 없음 상태를 반복하지 않는다.

**대안: URL만 정규화** — 홈으로 이동한 뒤 일반 Ask 링크를 누르는 정확한 사용자 흐름에서 쿼리가 사라진다.

**대안: 서버의 최신 스레드를 항상 기본 선택** — 사용자가 새 대화를 시작하려는 의도와 브라우저·기기별 작업 맥락을 구분할 수 없다.

### 3. 진행 중 메시지는 읽기 전용 생성 상태로 렌더한다

스레드 상세 응답은 `streaming` 상태를 반환하고, Ask 화면은 질문 버블 아래에 기존 답변 카드 어휘를 재사용한 생성 중 상태를 보여준다. 이 상태에는 발급 인용이 없으므로 마커·재시도·완료 답변 컨트롤을 렌더하지 않는다. 다음 상세 조회에서 최종 상태가 보이면 기존 `turnsFromMessages` 경로로 인용을 재수화한다.

## Risks / Trade-offs

- [Risk] 스트리밍 중 클라이언트가 라우트를 벗어나면 기존 요청의 최종 `done`을 새 Ask 컴포넌트가 직접 받지 못한다. → Mitigation: 복귀 컴포넌트는 상세 조회에서 `streaming`을 표시하고, 짧은 재조회로 최종 상태를 반영한다.
- [Risk] 세션 저장소의 삭제된·권한 없는 스레드 ID가 반복 사용될 수 있다. → Mitigation: 상세 조회의 403·부재 결과에서 즉시 키를 제거한다.
- [Risk] `ask_messages` 갱신 권한이 넓어지면 사용자가 자신의 최종 답변을 직접 변경할 수 있다. → Mitigation: 정책은 작성자·멤버십으로만 범위를 열고, 최종화 RPC는 상태 전이·멱등성을 검증하며 API는 RPC만 사용한다.
- [Risk] 새 제약이 기존 행 또는 배포 중 실행과 충돌할 수 있다. → Mitigation: 기존 상태만 가진 행을 보존하고, 새 상태·인덱스·RPC를 순서대로 추가하는 전진 전용 마이그레이션을 쓴다.

## Migration Plan

1. `0019` 마이그레이션으로 `streaming` 상태, `(workspace_id, client_turn_id)` 고유 제약·인덱스, 필요한 RLS 갱신, `start_ask_turn`·`finalize_ask_turn` RPC를 추가한다.
2. API를 초기 생성 → 첫 `meta.thread_id` → 기존 스트리밍 → 최종 확정 순서로 전환한다.
3. 대시보드가 새 메타데이터와 진행 중 메시지를 처리하고 세션별 Ask 링크 복원을 적용한다.
4. API RLS·멱등성 테스트와 대시보드 라우트 복귀 테스트를 통과시킨다.

롤백은 애플리케이션을 이전 버전으로 되돌리고 새 `streaming` 행이 없음을 확인한 뒤에만, 별도 후속 마이그레이션으로 새 RPC·정책·제약을 제거한다. 적용된 마이그레이션 파일은 수정하거나 삭제하지 않는다.
