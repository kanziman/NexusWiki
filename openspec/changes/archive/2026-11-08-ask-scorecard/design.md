## Context

배경과 동기는 `proposal.md`를 본다. 현재 `scripts/ask_replay.py`는 질문 30개를 SSE로 묻고 질문별 행(`rows`)과 요약(`summary`)을 JSON 한 파일로 저장한다. 행에는 `status`, `elapsed_ms`, 토큰, `cost_micros`, `dual_citation_rate`, `fabricated_anchor_count`, `keyword_hit`이 이미 있다. 부족한 것은 판정, 지연 집계, 누적 기록, 화면이다.

제약: 이 스크립트의 수치는 이력서와 쇼케이스에 인용되므로 집계가 조용히 틀리면 거짓 근거가 된다(`test_ask_replay_script.py` 머리말). 재생은 loopback 스택에만 붙는다.

## Goals / Non-Goals

**Goals:**
- 판정·집계 로직을 네트워크 없이 단위 테스트할 수 있는 순수 함수로 둔다.
- 화면 생성은 결과 파일만 읽는다. API·DB·공급자에 닿지 않는다.
- 학습 목적이므로 "어느 질문이 왜 떨어졌는지"를 한 화면에서 따라갈 수 있게 한다.

**Non-Goals:**
- 운영 트래픽 평가, 대시보드 제품 화면, 서버 실행형 웹앱.
- 인용 계약(`output-contract`) 자체의 판정 로직 변경. 여기서는 이미 계산된 필드를 읽기만 한다.
- 질문 세트 확장이나 LLM 판사 도입.

## Decisions

**1. 판정은 행 필드에서 파생한다. 재생 시점에 굳히지 않는다.**
`verdict(row, question)`을 순수 함수로 두고 행에서 계산한다. 결과 파일에 `verdict`를 저장도 하지만, 화면은 항상 같은 함수로 다시 계산한다. 기준이 바뀌어도 옛 결과 파일을 다시 채점할 수 있고, 옛 파일(판정 필드 없음)도 그대로 그려진다. 대안은 판정을 저장만 하는 방식이었으나 기준을 고칠 때마다 유료 재생이 필요해져 버렸다.

**2. 통과 기준의 구체 값.**
- "정상 완료"는 `status == "resolved"`만이다. `fallback`은 인용 계약 수리에 실패한 답이므로 불통과로 본다.
- "이중 인용 1개 이상"은 **답변 단위**로 본다: 답변이 실제로 인용한 앵커 중 위키 1개 이상과 원문 1개 이상(서로 다른 문장이어도 된다). 인용 이벤트의 `resolved` 목록 `kind`(`wiki`/`source`)에서 세어 행에 `cited_wiki_count`/`cited_source_count`로 기록한다. 구현 중 확인한 사실: 기존 `dual_citation_rate`는 "한 문장 안에 두 종류가 모두 있는 문장 비율"이라 답변 단위 기준과 다르다(`ask.py`의 `dual_cited_count`). 처음에는 `> 0`으로 대체했다가 spec 적합성 리뷰 r1에서 지적받아 이 필드로 바꿨다. 종류별 개수가 없는 옛 결과는 `dual_citation_rate > 0`으로 대체하고 이유에 그 사실을 밝힌다(더 엄격한 기준).
- `keyword_hit is None`(기대값 없음)은 그 기준을 건너뛴다.
- `answerable: false`인 질문은 `status == "no-evidence"`가 정답이다. 이 예외가 없으면 q30이 항상 실패로 보여 통과율이 구조적으로 29/30에 묶인다.
- 실패 이유는 고정 순서로 첫 번째만 적는다: 상태 → 위조 앵커 → 기대 사실 누락 → 이중 인용 없음. 한 줄 요구와 화면 폭 때문이다.

**3. 지연은 `elapsed_ms`의 p50/p95. 기존 `_percentile`을 재사용한다.**
지연은 SSE 시작부터 마지막 프레임까지 클라이언트가 잰 값이다. 서버 처리 시간이 아니고, 큐 대기와 네트워크가 섞인다. 화면 머리말에 이 뜻을 적는다. `_percentile`은 `int(fraction * n)` 인덱스 방식이라 n=30에서 p95가 29번째 값이다. 이 정의를 그대로 쓰고 문서에 적는다(보간 방식으로 바꾸면 기존 입력 토큰 p95와 정의가 갈린다).

**4. 누적 기록은 JSONL append, 위치는 `--scorecard` 인자(기본: `--out` 옆 `scorecard.jsonl`).**
한 줄 = 한 실행, 한 번 쓰고 고치지 않는다. 저장소 밖 재생 출력 디렉터리에 두어 합성 수치가 커밋되지 않게 한다. 줄에는 결과 파일 상대 경로를 넣어 화면이 상세를 찾는다. 질문·답변 본문은 넣지 않는다(상세는 결과 파일에서만 읽는다). 대안은 SQLite였으나 `tail`/`jq`로 바로 보이고 append-only 성질이 공짜인 JSONL이 학습용에 맞다.

**5. 모델명은 `usage_events`의 모델 값에서 읽는다.**
재생 스크립트는 모델을 모른다(`LLM_MODEL`은 서버 스크립트가 읽는다). `_ask_once`가 이미 `usage_events`를 조회하므로 `select`에 모델 컬럼을 더하고 첫 비어 있지 않은 값을 실행의 모델로 삼는다. 컬럼 이름은 구현 시 `0024_usage_trace.sql` 전후 스키마로 확인한다. 값이 없으면 `unknown`을 기록한다(스펙의 "알 수 없음" 시나리오).

**6. 화면은 단일 HTML 파일, 인라인 CSS/JS, 외부 의존 없음.**
`report` 하위 명령이 `scorecard.jsonl`과 결과 JSON들을 읽어 HTML 문자열 하나를 쓴다. 데이터는 `<script type="application/json">`에 넣고 작은 JS가 표를 그린다. 이 JSON은 `</script>`를 깨뜨릴 수 있으므로 `<`를 `<`로 이스케이프하고, 표 셀은 `textContent`로만 채운다(스펙의 "마크업을 실행하지 않음"). 실패 구분은 색만이 아니라 `✗ 실패`/`✓ 통과` 글자와 굵기를 함께 쓴다. 다크/라이트는 `prefers-color-scheme`를 따른다.
대안: sec01처럼 `http.server`로 띄우는 방식. 파일을 열기만 하면 되고 포트가 필요 없으며, 프로젝트 포트 규칙(544xx)과 충돌할 여지가 없어 정적 파일을 택했다.

**7. 재생 명령은 `scorecard`/`report`를 분리한다.**
`ask` 명령 끝에서 자동 append, `report` 명령은 읽기 전용 생성. `report`는 `httpx`·스택 코드를 타지 않아 오프라인에서 돈다(스펙 "Page generation spends nothing"). 기존 `ask`/`compare` 인자와 출력은 유지한다.

## Risks / Trade-offs

- **[판정 기준이 합성 샘플에 과적합]** 기대 사실은 키워드 포함 여부일 뿐이다 → 화면과 문서에 "합성 샘플, 키워드 기준"을 고정하고 운영 수치로 인용하지 않는다.
- **[n=30의 p95는 사실상 최댓값 근처]** → 지연 옆에 문항 수를 같이 보이고, 작은 차이는 의미 없다고 `ask-sample-replay.md`의 기존 경고를 재사용한다.
- **[LLM 답이 매번 달라 통과율이 흔들림]** sec01·03에서 본 현상과 같다 → 같은 label로 재실행한 줄이 나란히 쌓이므로 화면에서 범위로 읽게 한다. 반복 평균 기능은 범위 밖이다.
- **[`fallback`을 불통과로 보면 수리 경로가 정상 동작해도 점수가 깎임]** → 이유를 "수리 후 fallback"으로 구분해 적어 원인이 보이게 한다.
- **[결과 JSON이 크면 HTML이 커짐]** 30문항 × 답변 본문이 전부 들어간다 → 답변은 접기(`<details>`)로 두고, 실행 수가 많으면 상세는 선택한 실행만 렌더링한다.
- **[누적 파일 손상]** 중간 줄이 깨지면 이후 줄을 못 읽을 수 있다 → 줄 단위 파싱, 깨진 줄은 건너뛰고 화면에 개수를 표시한다.

## Migration Plan

DB·API·배포 변경 없음. 롤백은 `scripts/ask_replay.py`와 테스트 되돌리기로 끝난다. 기존 결과 JSON은 그대로 읽힌다.

검증 순서: (1) 기존 `after.json` 등 결과 파일로 판정·HTML을 오프라인 검증 → (2) 단위 테스트 → (3) 마지막에 실제 30문항을 한 번만 돌려(약 $0.75~$0.94) 누적 줄과 화면을 확인한다. 3단계는 지출이라 사용자 확인 후에만 한다.
