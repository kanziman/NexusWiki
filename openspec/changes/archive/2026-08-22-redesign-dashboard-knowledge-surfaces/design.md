## Context

`proposal.md`의 변경은 기존 화면 컴포넌트와 하나의 CSS 디자인 정본을 함께 건드린다. 소스 상세는 현재 `raw_sources` 한 행만 읽지만 새 표면은 `source_chunks`와 `wiki_pages.sources` 관계도 필요하다. 위키 리더와 Ask는 내부 WikiLink·인용 앵커를 보존해야 하므로 일반 마크다운 렌더러로 단순 치환할 수 없다.

요청 경로의 모든 데이터 조회는 기존 `createClient()`가 만든 사용자 세션을 사용해야 하며, `service_role`을 사용할 수 없다. 마크다운은 원문·LLM 출력에서 오므로 HTML 문자열 삽입과 실행 가능한 링크 프로토콜을 허용하지 않는다.

## Goals / Non-Goals

**Goals:**

- 원문→청크→위키→답변의 읽기 흐름을 같은 시각 언어와 직접 탐색 경로로 잇는다.
- 문서 구조를 React 요소로 안전하게 렌더링하면서 WikiLink와 이중 Citation의 기존 동작을 유지한다.
- 기존 API·RLS·디자인 토큰을 재사용하고 회귀를 컴포넌트/라우트 테스트로 고정한다.

**Non-Goals:**

- 위키 직접 편집, 원문 수정, 청크 재분할 UI를 추가하지 않는다.
- 새로운 마크다운 표준 전체나 임의 HTML을 지원하지 않는다.
- 소스-위키 역참조를 위한 새 RPC, 마이그레이션, 인덱스를 추가하지 않는다.
- 모바일 사이드바의 정보 구조나 전역 내비게이션 목적지를 바꾸지 않는다.

## Decisions

### Decision 1: 문서 표면은 허용 목록 기반 React 렌더러를 사용한다

세 가지 대안을 비교했다.

| 대안 | 데이터/API | 상태 관리 | 핵심 동작 | 컴포넌트 구조 | 기존 패턴 | 테스트성 |
| --- | --- | --- | --- | --- | --- | --- |
| 외부 GFM 렌더러 도입 | 변화 없음, 의존성 추가 | 단순 | 표준 지원 폭이 넓음 | 플러그인으로 WikiLink·인용 결합 필요 | 새 패턴 | 좋음 |
| HTML 변환 후 삽입 | 변화 없음 | 단순 | 구현량이 적음 | 문자열 후처리 필요 | `dangerouslySetInnerHTML` 금지와 충돌 | 취약 |
| 허용 목록 기반 React 렌더러 | 변화 없음 | 블록 파싱 상태만 로컬 | 필요한 문법만 명시적으로 지원 | WikiLink·인용 노드를 제자리 보존 | 기존 `resolveWikiLinks`와 일치 | 가장 직접적 |

허용 목록 기반 React 렌더러를 선택한다. 렌더링할 문법이 계약에 한정되고 원문 HTML을 실행하지 않으며, Ask 세그먼트 사이의 `CitationMarker` React 노드를 문자열로 되돌리지 않아도 된다. 외부 링크는 공통 URL 검증 함수가 `http`, `https`, `mailto` 및 안전한 상대 경로만 허용하고, 나머지는 라벨만 렌더링한다.

### Decision 2: 소스 상세은 서버에서 세 개의 RLS 조회를 병렬 조합한다

`raw_sources`, 해당 `source_chunks`, 워크스페이스의 `wiki_pages`를 요청자 client로 병렬 조회하고, 위키의 `sources` 원장에서 현재 source id를 참조하는 페이지만 고른다. 기존 테이블과 RLS가 이미 필요한 경계를 소유하므로 새 API/RPC를 만들지 않는다.

대안인 브라우저 후속 조회는 로딩 상태가 세 갈래로 분산되고 첫 화면에서 추적 관계가 완성되지 않는다. 새 서버 RPC는 대규모 워크스페이스에서 더 효율적이지만 이번 범위에 데이터베이스 계약과 배포 순서를 추가한다. 현재 방식은 v1 규모와 기존 서버 라우트 패턴에 맞고, 소스가 보이지 않으면 관련 데이터도 렌더 트리에 전달하지 않는다.

### Decision 3: 디자인 정본은 기존 CSS 파일을 유지하고 컴포넌트는 의미 구조를 소유한다

색상·간격·포커스·축소 사이드바·목록/리더 반응형 규칙은 `nexuswiki-design-system.css`에 둔다. 컴포넌트는 제목, 표, 상태, 버튼, 접근 가능한 이름과 같은 의미 구조를 소유한다. 별도 CSS module이나 화면별 토큰 복제는 같은 요소가 다시 갈라지게 하므로 선택하지 않는다.

### Decision 4: 활성 목차는 문서 heading id를 단일 원장으로 삼는다

본문과 목차가 같은 줄 인덱스 기반 id를 생성하고, 스크롤 위치에서 마지막으로 지난 heading을 활성화한다. 목차 선택은 해당 DOM heading을 부드럽게 스크롤하고 fragment를 갱신한다. 별도 라우트 상태나 저장 상태는 문서 내용 변경 시 stale해질 수 있어 만들지 않는다.

## Risks / Trade-offs

- [간이 마크다운 파서가 모든 GFM 경계를 지원하지 않음] → 지원 문법을 스펙에 명시하고 표·목록·인용·코드·링크·WikiLink·인용 마커 회귀 테스트를 둔다.
- [세 화면의 인라인 파싱이 서로 어긋날 수 있음] → URL 안전성은 공통 함수로 통합하고 동일 fixture로 핵심 문법을 검증한다. 이후 전체 파서 통합은 별도 리팩터링으로 남긴다.
- [워크스페이스의 모든 wiki page를 읽어 역참조를 계산함] → RLS와 `workspace_id` 필터를 유지하고, 규모가 커져 병목이 측정될 때 RPC/역참조 인덱스를 별도 change로 설계한다.
- [스크롤 이벤트가 긴 문서에서 반복 DOM 조회를 수행함] → passive listener를 사용하고 heading 수에만 비례하게 제한한다. 병목이 측정되면 `IntersectionObserver`로 교체할 수 있다.
- [디자인 변경이 기존 카피·상태 의미를 흐릴 수 있음] → 상태 계산과 기존 고정 카피는 그대로 재사용하고 테스트는 의미 텍스트와 접근 가능한 역할을 기준으로 둔다.

## Migration Plan

1. 화면 컴포넌트와 CSS를 함께 배포하며 데이터베이스 마이그레이션은 수행하지 않는다.
2. dashboard 테스트·typecheck·lint·production build와 OpenSpec strict validation으로 배포 전 회귀를 확인한다.
3. 문제가 발생하면 이 change의 UI 커밋을 되돌린다. 데이터나 API 계약 변경이 없어 별도 데이터 롤백은 필요 없다.
