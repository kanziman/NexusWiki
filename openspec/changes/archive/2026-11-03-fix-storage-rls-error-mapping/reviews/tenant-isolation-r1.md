## 추가 확인

- HTTP 400 전체를 403으로 바꾸지 않는다. 기존 code·전송 상태 판정이 없으면 JSON 객체의 statusCode 401/403만 거부로 처리하고, 다른 값·JSON 배열·null·파싱 실패는 기존 StorageUnavailable 경로로 남긴다(`storage.py:291-301`).
- 공급자 메시지나 객체 경로를 예외 필드에 추가하지 않는다. 새 테스트는 본문에 비공개 표식을 넣고 `WorkspaceForbidden`의 문자열·필드에 남지 않음을 검사한다(`apps/api/tests/test_user_storage.py:260-285`). 일반 오류가 거부로 바뀌지 않는 테스트도 업로드·삭제 모두에 있다(`:288-304`).
- 업로드의 KeyAlreadyExists 우선 분기와 삭제의 404 멱등 반환은 바뀌지 않았다. 권한 실패가 성공으로 삼켜지는 분기는 추가되지 않았다.
- delta spec의 코드 없는 권한 거부 시나리오는 401/403의 정수·문자열 조합으로 검사하고, 일반 장애 시나리오는 500·잘못된 타입·비객체 본문으로 구분한다. 기존 고정 403/502 렌더러는 수정하지 않는다.

## 검증 범위와 한계

코드·작업 트리 diff·계약·기존 오류 렌더 경계를 정적으로 검토했다. 호출자는 관련 단위·실DB 테스트 59개 통과와 Ruff·strict validation 통과를 보고했으며 전체 pytest를 다시 실행 중이다. 공유 DB·큐 테스트를 겹치지 않게 하기 위해 리뷰어는 별도 테스트 프로세스나 DB 쓰기를 실행하지 않았다. 이 pass는 필수 전체 스위트가 이미 통과했다는 주장이 아니다.

## 판정 근거

변경은 요청자 JWT와 기존 RLS 경계를 유지하면서 공급자의 새로운 권한 거부 표현을 기존 안전한 403 예외로 연결한다. 일반 장애와 공급자 오류 본문의 비공개 처리도 유지된다. 테넌트 격리·오류 매핑·멱등성에 새 위반을 찾지 못해 `pass`로 판정한다.
