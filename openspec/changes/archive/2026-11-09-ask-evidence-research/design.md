## Context

요구사항: proposal.md. 최초 범위 승인 후 포트폴리오용 결과 페이지가 추가 요청됐다.

현재 API Ask 서비스는 요청자의 UserDb로 검색·본문 조회를 수행하고, 워커의 인증된 `/internal/llm-chat`로 답변을 생성한다. 워커 요청은 문자열 messages만 받으므로 실제 tools 스키마와 tool_calls 처리를 추가해야 한다. 기존 워커에는 호출별 예산 예약과 사용량·중단 회계가 있다. 근거 0건이면 공급자를 호출하지 않는 기존 경로가 있다.

기존 재생 문서는 문서 재수집으로 위키가 달라져 비교가 오염된 사례를 기록한다. 이번 비교는 동일 수집 결과와 고정된 검색 정책에서 수행해야 한다.

## Goals / Non-Goals

- 목표: 모델이 첫 검색 내용을 보고 선택하는 제한된 재검색과 재현 가능한 비교 기록을 만든다.
- 목표: 합성 평가 기록으로 포트폴리오 페이지를 제공한다. 운영 원문·JWT·개인정보를 공개 데이터로 전달하지 않는다.
- 제외: 무제한 에이전트 루프, 임의 도구 등록, 주변 읽기 도구, RRF 변경의 동시 평가.

## Decisions

### D1. 실행 경계 선택 — 승인됨

| 비교 기준 | A. API가 도구 실행, 워커가 판단 호출 (권고) | B. 워커가 검색까지 실행 | C. API에서 공급자 직접 호출 |
| --- | --- | --- | --- |
| 데이터 구조 | 내부 LLM 요청에 고정 도구 스키마, 응답에 tool_calls 추가 | 워커에 사용자 검색 권한 전달 구조 필요 | API에 공급자 요청·사용량 구조 추가 |
| API 영향 | 공개 Ask 계약 유지, 내부 LLM 경계 확장 | 내부 검색 RPC/콜백 경계 추가 | API가 공급자 인증정보 소유 |
| 상태 관리 | API 요청 수명 안에서 1회 판단·최대 2검색 | API와 워커 사이 도구 상태 공유 | API 안에서 판단·검색·답변 관리 |
| 핵심 동작 | API가 검증된 query만 기존 검색 서비스에 전달 | 워커가 도구 루프와 검색을 소유 | API가 공급자 도구 응답을 직접 처리 |
| 구성 요소 | 기존 Ask 서비스 + 워커 LLM 전송 확장 | 워커 검색 클라이언트와 권한 경계 신설 | API 공급자 클라이언트·회계 신설 |
| 기존 패턴 일치 | JWT 검색은 API, 공급자 호출·회계는 워커 유지 | 워커가 사용자 조회 책임까지 보유 | 공급자 호출은 워커라는 기존 경계 변경 |
| 테스트 | 도구 응답 대역과 UserDb 격리·회계 검증 | 분산 호출과 권한 전달 검증 필요 | 기존 워커 회계와 중복 검증 필요 |

권고는 A다. 모델이 선택하는 것은 검색어뿐이며, API는 기존 요청의 workspace_id와 UserDb를 유지한다. 워커의 기존 예산 예약·실사용량·중단 처리를 판단 호출에도 적용한다. 도구 실행 결과를 모델에 돌려주는 추가 판단 루프 없이 병합한 근거로 별도 최종 답변을 만든다.

### D2. 제한된 판단과 실패 처리

- 서버 설정 `ASK_EVIDENCE_RESEARCH_ENABLED`의 기본값은 false다. OFF는 기존 경로를 유지한다. 요청자가 임의로 모드를 선택하는 공개 API 파라미터는 추가하지 않는다.
- 첫 근거가 0건이면 기존 no-evidence 경로를 유지한다. 근거가 있으면 기존 예산으로 조립한 내용을 판단 모델에 제공한다. 판단은 현재 답변 모델과 동일한 모델을 사용한다.
- 워커는 고정된 search_evidence 도구 정의와 tool_choice auto로 한 번 호출한다. API는 전체 tool_calls를 수신·검증한 후 실행한다. 자연어 또는 JSON 흉내를 실제 도구 호출로 해석하지 않는다.
- query만 허용하고, 공백 제거 후 1~500자, 알 수 없는 인자 금지, 최대 2개 호출을 강제한다. 호출 수 초과·잘못된 이름·인자는 배치 전체를 실행하지 않는다. 동일 검색어는 한 번만 실행한다.
- 판단과 재검색을 합쳐 15초 제한을 둔다. 유효한 2개 검색은 순서대로 실행하고, 완료된 검색의 근거만 반영한다. 일반 타임아웃·잘못된 호출·검색 일시 실패는 기존 근거로 답변한다. 인증·권한 거부는 삼키지 않고 기존 401/403 처리로 종료한다. 예산 거부는 추가 유료 작업을 중단하고 기존 예산 오류 경로로 종료한다. 클라이언트 취소는 전파한다.
- 최종 답변 전까지 도구 델타를 외부 SSE에 내보내지 않는다. 판단 결과의 자연어는 답변으로 사용하지 않는다.
- 2026-11-09 추가 결정: 판단 응답이 무효(출력 상한 `length` 종료, 호출 수 초과 등)여도 API는 판단 스트림을 끝까지 읽은 뒤 실패로 처리한다. 중간에 닫으면 워커가 이미 받은 실사용량을 불완전으로 정산해, 비용이 모두 기록된 턴도 eval에서 측정 장애가 된다(q28 실측). 실패는 보유 근거로 복구하되 턴 보고서의 `failure_reason`과 `ask.research_failed` 경고 로그에 고정 사유 토큰만 남긴다. 판단 출력 상한 256은 바꾸지 않았다.

### D3. 병합·인용·관측

- 쿼리별 RRF 점수는 서로 직접 비교하지 않는다. 초기 검색과 추가 검색별 후보 목록을 라운드로빈으로 합쳐 동일 type/document_id는 최초 1개만 보존하고, 기존 이중 근거 선택 및 토큰 예산을 다시 적용한다. 최종 선택된 근거에 별칭을 새로 발급한다.
- 판단 입력과 최종 답변 입력은 각각 기존 컨텍스트 상한 안에 둔다. 두 호출의 합계 토큰이 늘어나는 점은 비용으로 드러낸다.
- 턴 보고서에 모드, 판단 상태, 요청/실행 호출 수, 추가·최종 근거 식별자, 소요 시간, 제한·실패 사유를 기록한다. 질문·검색어·본문·JWT는 일반 로그에 추가하지 않는다. 공급자 호출 비용은 기존 워커 회계로 각각 기록한다.
- eval 전용 결과 파일은 첫 선택 근거와 최종 예산에 포함된 근거를 문서 정답에 매핑할 수 있어야 한다. 실제 판단에 쓰인 초기 근거가 실패했는지와 최종 문맥에 정답이 들어왔는지를 구분한다.

### D4. 적용 전후 평가

- 별도 합성 fixture에 기존 30문항 회귀와 비교형 6문항·표현 불일치 6문항을 포함한다. 전용 12문항은 기대 문서 전체, 필수 사실, 질문 유형을 명시한다. 결과를 보기 전 fixture 해시와 판정 규칙을 고정한다.
- OFF 기준선을 먼저 실제 실행하고, 구현 후 ON을 실행해 총 1쌍을 얻는다. 사용자 비용 절감 요청(2026-11-08)으로 완료된 첫 쌍만 사용하고 추가 반복은 하지 않는다. 문서·청크·위키·링크·임베딩 스냅샷 해시, 모델 및 설정, 프롬프트 해시, RRF 정책 전체 해시, fixture 해시를 비교한다. 코드 revision은 양쪽을 각각 기록한다. 조건이 다르면 유효 비교로 취급하지 않는다. 반복 안정성은 미측정이며 단일 합성 쌍의 탐색 결과로 한정한다.
- 전체 기대 문서가 첫 문맥에 없던 전용 문항을 복구 대상 분모로 삼는다. 최종 문맥에 전체 기대 문서가 들어오면 근거 복구, 필수 사실·이중 인용까지 통과하면 답변 복구로 별도 집계한다. 분모 0이면 복구율은 null이며 성공으로 주장하지 않는다.
- 질문별 근거·최종 답변 판정, ON/OFF 승패 변화, 거절·위조 인용, 판단/임베딩/답변/수리의 전체 토큰·비용, 총 지연 및 첫 답변 토큰 지연 p50/p95를 기록한다. 측정 장애는 복구로 세지 않고 별도 집계한다. 동일 문항의 세 번 실행을 독립 문항처럼 부풀리지 않는다.
- 채택 기준: 1쌍에서 답변 복구가 1건 이상이고 전체 통과 건수가 OFF보다 증가, 기존 30문항 통과 건수 감소 없음, 위조 인용 증가 없음, 문항당 평균 비용 증가 50% 이하, p95 총 지연 증가 15초 이하. 기존 수치 기준은 유지하되 반복 횟수 축소는 결과 확인 후 사용자 요청으로 결정됐음을 공개한다. 표본이 작으므로 반복 안정성이나 통계적 우월성을 주장하지 않는다. 기준 미달이어도 결과를 공개하고 기본 OFF를 유지한다. 기준 통과 후 기본 ON 전환은 이번 범위에서 하지 않는다.

### D5. 포트폴리오 결과 페이지

- 기존 `/showcase/controlled-ai`와 연결되는 로그인 없는 `/showcase/evidence-research`를 추가한다. 현재 대시보드의 Next.js 구조와 디자인을 따른다. 별도 호스팅 시스템은 추가하지 않는다.
- 페이지는 빌드 시 포함하는 버전 있는 공개 JSON만 읽고 운영 API·DB·모델을 호출하지 않는다. 공개 export는 허용 필드 목록으로 합성 질문·정답 요약·문항별 판정·집계·해시·revision·모델·실행시각·제약을 선택한다. 자격증명·workspace UUID·공급자 generation id·운영 본문은 제외한다.
- 상단에 합성 평가와 채택 결과를 표시하고, OFF/ON 품질·비용·지연 비교, 조건 일치 여부, 문항별 전후 결과와 복구/회귀 필터, 평가 방법·원본 공개 JSON 다운로드를 제공한다. 값이 없으면 미측정으로 표시하고 0으로 채우지 않는다.
- 결과 데이터가 없거나 조건 불일치이면 개선 수치를 표시하지 않는다. 최종 산출물은 실제 측정 결과를 포함해야 한다. 배포는 별도 사용자 요청 전까지 하지 않고 코드·로컬 검증까지 수행한다.

## Migration Plan

서버 플래그 기본 OFF로 내부 LLM 도구 전송과 API 경로를 배포할 수 있게 한다. 이번 작업에서는 합성 스택에서만 ON 평가하며, OFF로 즉시 기존 경로로 돌아갈 수 있어야 한다. DB 스키마 변경 필요 여부는 기존 보고서 JSON과 회계 재사용을 먼저 확인하고 결정한다.

## 승인 및 리뷰 범위

- 요구사항·D1 아키텍처·최종 설계는 사용자가 승인했다. task 분해 승인은 별도 게이트다.
- 사용자 명시 요청으로 이번 change의 tenant-isolation-reviewer 리뷰 게이트는 생략한다. 격리·권한 검증 테스트는 유지하고 spec-conformance-reviewer는 수행한다.

## Risks / Trade-offs

- 판단 호출로 도구 미사용 질문도 비용·첫 토큰 지연이 증가한다 → OFF/ON 전체 질문 비용과 지연에 포함한다.
- RRF 작업과 같은 로컬 DB·워커 포트를 사용하면 평가가 섞인다 → 독립 스택과 실행 시점 포트 점유 확인이 필요하다.
- 작은 합성 표본의 개선을 일반화할 수 없다 → 포트폴리오 페이지에 표본 수·실행 횟수·한계를 결과와 함께 표시한다.
