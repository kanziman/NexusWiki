## Why

위키가 답변 품질에 더하는 기여와, 문서 제목을 붙인 임베딩의 효과를 아직 분리해 측정하지 않았다. RRF v2의 검색 개선(#231) 뒤 같은 수집 결과에서 두 요인을 교차 비교해, 기본 검색 방식을 바꿀 근거와 한계를 남긴다. 추적 이슈: https://github.com/kanziman/NexusWiki/issues/232.

## What Changes

- 검색 근거 `source_only` / `wiki_only` / `both`와 임베딩 입력 `body` / `title_body`를 교차한 6조건 실험을 추가한다.
- 현재 원문·위키·청크·좌표를 고정하고, 실제 원문 제목 또는 위키 페이지 제목을 임베딩 입력에만 붙인 벡터를 비교한다. 제목은 정답 문항에서 만들지 않는다.
- 첫 실험은 제목만 붙인다. `문서: <실제 제목>\n<청크 본문>`을 쓴다. 실제 섹션 추출은 확장 후보로 남기며, 섹션을 추측하거나 조건마다 다르게 추가하지 않는다.
- 수집 스냅샷·fixture·청크 경계·질의 벡터·모델과 공급자·RRF v2·그래프 설정·k·프롬프트·컨텍스트 예산을 고정하고 실행 조건과 입력 해시를 기록한다.
- 검색 6조건을 먼저 측정하고, 사전 선택 규칙과 비용 상한을 정한 뒤 유망 조건의 답변만 재생한다. 검색 미적중·실행 장애·의도된 단일 근거 조건을 구별한다.
- 원문만·위키만은 진단 실험으로 표시한다. 이중 인용이 불가능한 조건의 결과를 기존 제품 성적표의 이중 인용 통과율과 직접 비교하지 않는다. 제품 기본 모드와 채점 계약은 유지한다.
- append-only 결과·문항별 실패/복구·비용·한계를 저장하고, eval 작업 #230이 공개 허용 필드만 가져갈 수 있는 별도 실험 자료로 연결한다. 재검색 OFF/ON 42문항·3쌍 실험과 합산하지 않는다.

## Capabilities

### New Capabilities

- `retrieval-ablation-evaluation`: 동일 수집의 6조건 비교, 임베딩 입력 구별, 진단 조건별 판정과 비교 가능성 검증, 재사용 가능한 결과 기록.

### Modified Capabilities

없음. 운영 검색·임베딩 기본값, 기존 Ask 이중 인용 계약과 성적표 판정은 바꾸지 않는다. 실험 구현 구조는 계획 게이트 2에서 결정한다.

## Impact

- 예상 코드 범위: 실험 러너·입력 구성·격리된 벡터 기록·관련 테스트. 실제 파일 분해와 저장 구조는 설계 승인 뒤 확정한다.
- 기존 구현 확인: `apps/worker/src/worker/handlers/embed.py`는 원문 `content`와 위키 `chunk.content`를 임베딩한다. `Chunk`에는 섹션 필드가 없다.
- 기존 임베딩 버전은 모델·공급자 기반이다. 실험 입력 방식과 제목 변경을 구별하는 버전·해시가 추가로 필요하다. 본문이 같다는 이유만으로 제목이 바뀐 벡터를 재사용하지 않는다.
- 공유 운영 데이터와 다른 세션의 재검색 worktree는 수정하지 않는다. 공개 페이지 구현과 배포는 #230에서 다룬다.
- 범위 밖: q06/어휘 검색 수정(#195 A), 임베딩 실패 상태 개선(#195 C), 크레딧·비용 예약 복구, 재검색 도구, 회귀 CI와 모델 비교. 회귀 관문·평가 신뢰도 보강은 이 기록을 소비하는 후속 작업이다.
- 유료 호출은 별도 실행 승인 전까지 하지 않는다. 검색 임베딩·제목 벡터 생성·선택 답변 재생의 예상 비용과 상한은 최종 설계에서 제시한다.

## 승인 상태

요구사항과 용어(게이트 1): 사용자가 6조건 구성, 임베딩 입력에만 머리말 추가, 제목 우선·실제 섹션만 확장, 버전·해시 분리와 검색 선행 측정에 “응”으로 승인했다. 구조(게이트 2)는 실험 전용 벡터 + 프로세스 내 하네스 추천안으로 승인됐고, 사용자가 “추천안으로 한번에 끝까지 진행”을 지시해 최종 설계(게이트 3)와 수직 task(게이트 4)를 함께 확정했다(2026-11-08). apply와 유료 실행은 아직 승인 전이다.
