## Context

RRF v2(#231) 채택 측정은 546xx 로컬 스택의 같은 수집 결과(합성 문서 8개 · 위키 13쪽 · 질문 30개, `scripts/fixtures/ask_replay.v1.json`) 위에서 진행했고, 그 Docker 볼륨과 기록(`.worktrees/rrf-evidence-20261108/`)이 보존돼 있다. 이 change는 그 수집 결과를 다시 만들지 않고 6조건을 비교한다.

확인한 코드 사실:

- 검색은 `RetrievalService`(`apps/api/src/api/services/retrieval.py`)의 1차 4채널(`wiki_vector` · `source_vector` · `wiki_lexical` · `source_lexical`)과 선택적 그래프다. 정책은 `RetrievalPolicy`(`packages/core/src/nexuswiki_core/retrieval_policy.py`)에 있고 채널을 끄는 필드는 없다.
- `AskService`는 `RetrievalService`와 LLM 스트림 클라이언트를 생성자로 주입받는다. 컨텍스트는 `select_dual_evidence`가 위키·원문을 절반씩 고르고 빈자리는 다른 종류로 채운다. 따라서 단일 근거 조건에서도 컨텍스트 크기(k=8)는 유지된다.
- 답변 품질 검사(`check_answer_contract`)는 인용 개수와 위조 앵커만 본다. 위키 인용이 없다는 이유로 수리 호출이 붙지 않으므로 `enforce`를 모든 조건에 그대로 둔다.
- 워커 임베딩은 원문 `content`와 위키 청크 `chunk.content`만 쓰고, 버전은 `<model>@<provider>-v1`이다(`apps/worker/src/worker/embedding.py`). 원문 청크의 벡터는 `source_chunks`의 단일 컬럼이라 두 입력을 동시에 담을 수 없다.
- `scripts/benchmark_retrieval.py`는 `RetrievalService`를 프로세스 안에서 돌리고 로컬 DB를 `docker exec psql`로 호출하는 기존 패턴이다.
- `scripts/ask_replay.py retrieval-eval`은 정답 문서 판정 규칙(원문 근거는 raw_source, 위키 근거는 `wiki_pages.sources`)을 이미 갖고 있다.

## Goals / Non-Goals

**Goals:**

- 같은 수집 결과에서 근거 범위 3종 × 임베딩 입력 2종의 검색 성능을 비교한다.
- 위키가 답변에 더하는 기여를 원문만 조건과의 답변 비교로 측정한다.
- 결과를 append-only 기록으로 남기고 #230이 공개 허용 필드만 가져가게 한다.

**Non-Goals:**

- 운영 임베딩 입력이나 검색 기본값 변경. `title_body`가 이겨도 채택은 별도 change다.
- 섹션 머리말. 첫 실험은 제목만 쓰며 섹션은 별도 입력 버전으로 남긴다.
- q06·어휘 검색 수정(#195 A), 임베딩 실패 상태 개선(#195 C), 크레딧·비용 예약 복구.
- 재검색 도구, 회귀 CI 관문, 모델 비교, 평가 신뢰도 보강(반복 측정 · 실패 원인 분류 확장 · 거절 성능 분리). 마지막 둘은 이 기록을 소비하는 후속 작업이다.
- eval 공개 페이지 구현과 배포(#230).
- 새 수집. 보존된 수집 결과가 없거나 손상됐다면 이 change 안에서 다시 만들지 않고 멈춘다.
- 마이그레이션. 실험 저장소는 로컬 전용이며 `supabase/migrations/`에 넣지 않는다.

## Decisions

### D1. 실험 전용 벡터 저장소와 프로세스 내 하네스 (Gate 2 승인)

새 스크립트 `scripts/retrieval_ablation.py`가 보존된 수집 결과를 읽어 실험을 수행한다. `title_body` 벡터는 로컬 DB의 실험 전용 스키마 `ablation`에 둔다. 스키마는 스크립트가 시작 시 만들고, 마이그레이션에 넣지 않는다. 운영 함수와 RLS 정책 어디에서도 이 스키마를 참조하지 않으므로 운영 요청은 실험 벡터를 읽을 수 없다.

검색은 `RetrievalService`를 프로세스 안에서 만들고, 그 DB 어댑터가 벡터 채널 RPC(`search_chunks` · `search_wiki_embeddings`) 호출을 조건에 맞는 벡터 원천으로 보낸다. `body` 조건은 운영 RPC를 그대로 부르고, `title_body` 조건은 같은 SQL 형태(코사인 거리 정렬, `hnsw.iterative_scan = strict_order`, 같은 후보 상한)를 `ablation` 테이블에 적용한 실험 함수를 부른다. 어휘 채널은 두 입력 모두 운영 RPC를 그대로 쓴다.

답변 재생은 `AskService`를 프로세스 안에서 만들고 위 `RetrievalService`를 주입한다. LLM 스트림은 운영과 같은 워커 내부 경로를 써서 예산 회계를 우회하지 않는다.

기각한 대안:

- **워크스페이스 복제 후 재임베딩**: 운영 RPC를 그대로 쓰는 장점은 있다. 하지만 원문 · 청크 · 위키 · 근거 · 링크를 새 id로 복사해야 하고, 정답 문서와 인용 좌표를 비교하려면 id 변환이 필요하다. 또 워커와 API에 실험용 설정이 들어간다.
- **같은 행의 벡터를 교체했다가 복원**: id와 RPC가 그대로라는 장점은 있다. 하지만 중단되면 로컬 DB가 `title_body` 상태로 조용히 남고, "실험 벡터는 운영 임베딩과 분리" 요구에 정면으로 어긋난다.

### D2. 벡터 SQL 복제의 어긋남은 동등성 검사로 막는다

D1의 대가는 벡터 검색 SQL의 복제다. 실험 함수가 운영 함수와 어긋나면 `title_body`의 차이가 입력 효과인지 SQL 차이인지 구별할 수 없다. 그래서 측정 전에 **`body` 벡터를 `ablation` 테이블에도 복사해** 실험 함수로 검색하고, 모든 질의에서 운영 RPC와 채널별 순위·거리가 같은지 확인한다. 하나라도 다르면 측정하지 않고 중단한다. 이 검사 결과는 기록에 남는다.

### D3. 근거 범위는 정책의 활성 채널 집합으로 표현한다

`RetrievalPolicy`에 `enabled_channels` 필드를 추가한다. 기본값은 1차 4채널 전부이므로 운영 동작과 `policy_content` 해시 대상이 바뀌지 않게, 기본값일 때는 해시 입력에서 빠지도록 한다. 꺼진 채널은 `_disabled_meta`처럼 "의도적 비활성"으로 기록하고, 실패 메타와 섞지 않는다.

| 범위 | 활성 채널 |
| --- | --- |
| `source_only` | `source_vector` · `source_lexical` |
| `wiki_only` | `wiki_vector` · `wiki_lexical` |
| `both` | 1차 4채널 |

그래프는 모든 조건에서 운영 기본값(`graph_enabled = false`)으로 고정한다. 그래프는 위키 링크 기반이라 `source_only`에서 켤 수 없고, 조건마다 다르게 두면 비교가 깨진다.

기각한 대안: 하네스 안에서 채널 결과를 지우는 방식. 정책 버전과 메타에 흔적이 남지 않아 기록만 보고 어느 조건인지 확인할 수 없다.

### D4. 입력 형식과 벡터 식별

- 입력 형식 `title_body-v1`: `문서: <title>\n<chunk body>`. 원문 청크는 `raw_sources.title`, 위키 청크는 `wiki_pages.title`을 쓴다. 제목이 비어 있으면 그 청크는 실패로 기록하고 본문만으로 대체하지 않는다.
- `ablation` 행은 `(kind, chunk_ref, input_format, embedding_version, text_sha256)`로 식별한다. 같은 키가 이미 있으면 재사용하고, 하나라도 다르면 새로 만든다. 제목만 바뀌어도 `text_sha256`이 바뀌어 재사용되지 않는다.
- 질의 벡터는 질문마다 한 번 만들어 기록에 해시와 함께 고정하고 6조건 모두 같은 벡터를 쓴다. 질의 임베딩이 하나라도 실패하면 그 상태로 고정하지 않고 멈춘다. 실패를 담은 채 고정하면 일시 장애가 모든 조건의 실행 장애로 굳기 때문이다(첫 실행에서 30건 모두 502로 실패한 파일이 만들어진 뒤 추가한 규칙).

### D5. 고정 입력 해시와 비교 거부

기록의 `fixed_inputs`에 다음 해시를 둔다: 수집 스냅샷(원문 id·제목·청크 내용 해시, 위키 id·제목·본문 해시의 정렬된 목록), 질문 fixture, 청크 경계, 질의 벡터, 임베딩 모델·공급자, 정책 버전(`hybrid-rrf-v2`), 그래프 설정, k, 답변 프롬프트 버전, 컨텍스트 예산. 비교 명령은 조건 기록 사이에서 이 값이 하나라도 다르면 다른 항목을 이름으로 보이고 거부한다.

### D6. 판정

- 검색: 질문·조건마다 정답 문서의 hit@8, 첫 적중 순위, 원문·위키 각각의 적중을 센다. 정답 판정 규칙은 `retrieval-eval`과 같다.
- 분류 순서: 질의 임베딩 실패나 활성 채널 실패가 있으면 **실행 장애**, 아니면 정답 미적중이면 **검색 미적중**, 단일 근거 조건에서 반대 종류 근거가 없다는 이유만으로 떨어지는 경우는 **의도된 단일 근거**다.
- 답변: 기대 사실 포함(기존 `keyword_hit`)과 위조 앵커 수를 기록한다. 이중 인용 판정은 `both` 조건에만 붙인다. `source_only` · `wiki_only` 결과에는 `diagnostic: true`를 붙이고 요약 표에서도 "진단"으로 표시한다.
- 답할 수 없는 문항(`doc: none`)은 검색 단계에서 집계에서 제외하고, 답변 단계에서는 기존 거절 판정을 따로 보고한다.
- 복구·회귀: 같은 범위에서 `body` → `title_body`, 같은 입력에서 `source_only` → `both`의 문항별 적중 변화를 기록한다.

### D7. 사전 등록 선택 규칙과 비용 상한

검색 측정 전에 아래 규칙을 기록 파일에 써 두고 해시를 남긴다. 답변 재생 명령은 이 사전 등록 파일의 생성 시각이 검색 기록보다 늦으면 거부한다.

1. `source_only × body`와 `both × body`는 항상 재생한다. 위키 기여를 답변 수준에서 재는 핵심 비교다.
2. `both × title_body`는 검색 단계에서 `both × body` 대비 hit@8이 같거나 높고, 새로 생긴 검색 미적중이 1문항 이하일 때만 재생한다.
3. `wiki_only`와 `source_only × title_body`는 검색만 잰다.

예상 비용(2026-11-08 재생 실측 기준: `anthropic/claude-sonnet-4.6`, 문항당 약 $0.027, 30문항 1회 $0.75~$0.94):

| 단계 | 호출 | 예상 | 상한 |
| --- | --- | --- | --- |
| 제목 벡터 + 질의 벡터 | 임베딩만 | $0.01 미만 | $0.10 |
| 답변 재생 | 최대 3조건 × 30문항 = 90턴 | 약 $2.5~$2.8 | $3.00 |

합계 상한 $3.10. 상한에 닿으면 남은 문항은 "미실행"으로 기록하고 멈춘다. 재생 DB의 월 한도($5)에 기존 사용액이 쌓여 있으면 402가 날 수 있다(RRF v2 재생에서 실제로 발생). 이때는 한도를 임의로 올리지 않고, 사용자 승인 후 재생 전용 로컬 한도를 일시 조정했다가 복원한다. 유료 실행 자체도 별도 승인 전에는 하지 않는다.

### D8. 기록 형식과 공개 필드

- 기록은 `retrieval-ablation-v1` 스키마의 JSON 파일이다. 이미 있는 경로는 덮어쓰지 않는다. 원본 기록은 Git에서 제외되는 worktree 밖 경로에 두고, 해시와 요약만 `docs/ops/`에 남긴다.
- `experiment: "retrieval-evidence-ablation"`을 넣어 재검색 OFF/ON 실험과 구별한다. 요약 명령은 다른 실험 식별자의 기록을 함께 받으면 거부한다.
- `publishable` 객체에 조건별 집계, 문항 id별 판정·분류, 비용 합계, 한계 문장만 둔다. 질문 원문, 답변 본문, 근거 본문, 워크스페이스 id, 토큰은 넣지 않는다.

## Risks / Trade-offs

- [벡터 SQL 복제로 실험 경로가 운영과 어긋남] → D2 동등성 검사가 실패하면 측정하지 않는다.
- [합성 문서 8개 · 30문항이라 차이가 우연일 수 있음] → 문항별 복구·회귀를 같이 보고, 기록과 요약에 표본 한계를 적는다. 반복 측정은 후속 작업이다.
- [LLM 답변은 매번 달라 한 번의 재생 차이가 잡음일 수 있음] → 결론은 검색 단계 지표를 우선하고, 답변 비교는 보조 근거로 표시한다.
- [단일 근거 조건에서 컨텍스트 구성이 바뀌어 프롬프트 효과와 섞임] → `select_dual_evidence`의 빈자리 채우기로 k는 같다. 종류 구성이 다르다는 점은 한계로 기록한다.
- [보존된 수집 결과가 없거나 바뀜] → 시작 시 수집 스냅샷 해시를 계산해 RRF v2 기록과 대조하고, 다르면 멈춘다.
- [`enabled_channels` 추가가 운영 정책 해시를 바꿈] → 기본값일 때 해시 입력에서 빼고, 기존 정책 해시가 그대로인지 테스트로 고정한다.

## Migration Plan

DB 마이그레이션은 없다. `ablation` 스키마는 로컬 스택에서만 스크립트가 만들고, `cleanup` 하위 명령으로 지운다. 운영 코드 변경은 `RetrievalPolicy.enabled_channels`와 `RetrievalService`의 비활성 채널 처리뿐이며 기본값에서 동작이 같다. 되돌리기는 커밋 revert로 충분하다.
