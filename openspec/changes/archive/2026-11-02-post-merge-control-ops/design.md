## Context

배경과 승인된 요구사항은 `proposal.md`를 따른다. 현재 main은 #173의 squash 커밋 `184c5b4`이며 공개 증거의 수정 후 해시는 브랜치 커밋이다. 이번 세션에서 main의 합성 시나리오 4개를 재측정해 기존 `after.values`와 같음을 확인했다. 클라우드 복구 상태는 사용자가 전달한 보고이며 이번 세션이 직접 클라우드에서 확인한 결과가 아니다.

## Goals / Non-Goals

- 목표: 공개 증거의 커밋 출처를 main에서 찾을 수 있게 하고, 운영 기록의 출처와 미확인 항목을 구분하며, DB 선적용 조건을 PR 계약으로 남긴다.
- 비목표: 운영 DB 적용, 실제 계정의 유료 호출, 워커·원문 복구, Railway 변수 변경, CI 또는 배포 자동화 구현, PR 머지.

## Decisions

### D1. 측정 코드가 포함된 main 커밋을 가리킨다

`184c5b4`의 깨끗한 측정 대상 코드로 재측정한 결과와 기존 값을 비교하고 `after.commit`만 해당 해시로 갱신한다. 이 후속 문서 커밋의 해시를 가리키면 자기 참조가 되어 다시 갱신해야 하므로 선택하지 않는다. 이후에도 측정 대상 코드가 같으면 증거의 해시를 매 커밋마다 바꾸지 않는다.

### D2. 보고된 사실과 직접 검증을 구분한다

`docs/ops/migration-0023-0026-record.md`에 사용자 제공 복구 보고임을 명시한다. `0026` 적용·대기 0건과 API health 및 위조 토큰 401은 그 출처로 기록한다. 적용 전 최신 번호 `0021`은 보고된 사실로 정정하되, 실제 push 대상 파일 목록이나 원격 함수 권한은 추측하지 않는다. 실제 로그인·Ask·수집·워커와 장애 구간의 피해는 미확인으로 남긴다. 과거 아카이브나 PR 본문은 당시 판단 기록으로 보존한다.

### D3. 호환성 확인을 전제로 하는 수동 운영 게이트

계약의 정본은 `pull-request-workflow`에 추가하고, Railway 체크리스트는 이 계약을 참조하며 운영자가 사용할 순서를 안내한다. 원격 원장 확인 → dry-run → 호환성 확인 → 승인된 DB 적용 → 적용 결과 확인 → 머지 → 배포 후 실제 흐름 확인 순서다. 에이전트의 DB 쓰기 권한은 별도로 판단한다.

항상 머지부터 하는 방식은 자동 배포가 DB보다 먼저 나가는 문제를 되풀이한다. 모든 DDL을 무조건 먼저 적용하는 방식도 이전 코드를 깨뜨릴 수 있어 채택하지 않는다. 비호환 변경은 호환 단계로 분리하거나 자동 배포를 통제하는 별도 승인 계획을 요구한다. 이번 작업에는 데이터·API·UI 구조 선택이 없어 인위적인 세 가지 아키텍처 비교는 하지 않는다.

## Risks / Trade-offs

- 수동 게이트는 기술적으로 머지를 차단하지 못한다 → PR에 확인 결과를 기록하도록 하고 자동화는 후속 범위로 남긴다.
- 사용자 보고를 독립 검증으로 오해할 수 있다 → 출처와 미확인 항목을 같은 기록에 명시한다.
- 문서 PR도 main 머지 시 자동 배포될 수 있다 → 이 PR에는 새 마이그레이션이 없음을 명시하고 머지는 수행하지 않는다.

## Migration Plan

이 change는 DB 스키마를 변경하지 않는다. 증거·문서 검증과 리뷰 후 정본을 동기화하고 아카이브해 후속 PR에 포함한다. 되돌려야 하면 해당 증거·문서 변경만 별도 커밋으로 되돌린다. 운영 DB 롤백은 해당하지 않는다.
