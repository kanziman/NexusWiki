## Context

현재 `Dropzone`의 파일 탭은 하나의 `File`과 공통 제목을 보관한 뒤, 기존 raw-byte 파일 등록 endpoint를 한 번 호출한다. 여러 파일을 한 번에 선택할 수 있어도 API, Storage, 중복 처리, RLS, job lifecycle은 파일별 계약을 유지해야 한다. 요구사항은 `proposal.md`와 delta specs를 따른다.

## Goals / Non-Goals

**Goals:**

- 파일마다 독립적인 클라이언트 상태와 결과를 유지하는 다중 등록 흐름을 만든다.
- 파일명에서 안전하게 제목을 만들고 Unicode를 보존한다.
- 기존 단일 파일 endpoint로 파일별 요청을 보내며, 성공한 source의 job을 기존 목록 갱신 흐름에 연결한다.

**Non-Goals:**

- 배치 업로드 endpoint, DB 스키마, Storage/RLS 정책, job 모델 변경
- URL·텍스트 탭의 다중 등록
- 이미 완료된 위키 slug 라우팅 변경의 재구현

## Decisions

### 파일별 상태 레코드

선택 또는 drop 즉시 각 파일을 고유 클라이언트 항목으로 변환하고 파일, filename-derived title, 상태, 사용자 안전 오류 메시지를 보관한다. 단일 `selectedFile`과 공유 제목 상태를 대체한다. 이는 결과가 섞인 경우에도 어떤 파일이 실패했는지 분명히 하며, 목록 UI가 색상 외 텍스트 상태를 제공하도록 한다.

대안인 전체 배치 상태 하나는 부분 실패를 정확히 나타내지 못해 채택하지 않는다.

### 기존 per-file endpoint와 제한된 동시성

각 파일은 기존 `/sources/file` raw-byte 요청으로 등록한다. 클라이언트는 작은 고정 동시성 제한을 적용해 네트워크와 서버 부하를 제한하되, 파일 한 건의 실패를 독립적으로 처리한다. 새 배치 계약은 API와 worker의 격리·중복 규칙을 중복 구현하게 되므로 만들지 않는다.

### 파일명 제목 파생

마지막 확장자만 제거해 제목을 만들고, 파일명이 확장자로만 구성된 경우에는 원래 이름을 유지한다. 문자열을 ASCII로 변환하거나 slug로 정규화하지 않는다. 서버는 기존 제목 검증의 최종 판정자다.

## Risks / Trade-offs

- [브라우저가 큰 파일 목록을 한꺼번에 선택] → 제한된 동시성 및 파일별 진행 상태로 요청 폭주와 불명확한 대기 상태를 줄인다.
- [같은 파일이 중복 선택됨] → 각 요청의 기존 중복 판정을 유지하고 해당 항목만 duplicate로 표시한다.
- [한글 filename에서 생성된 위키 slug 탐색] → 이미 검증된 Unicode slug 라우팅 회귀 시나리오를 dashboard 통합 검증에 포함한다.
- [파일 업로드 중 화면 이탈] → 기존 단일 요청과 같은 브라우저 취소 동작을 유지하며, 서버에 접수된 작업의 처리 상태는 Sources 목록에서 다시 조회한다.

## Migration Plan

1. component와 테스트를 파일별 상태 모델로 전환한다.
2. 기존 dashboard 테스트, typecheck, lint를 실행한다.
3. 기존 단일 파일 업로드 호환성과 다중 파일 부분 실패를 검증한다.

롤백 시 다중 선택 UI만 되돌리면 기존 per-file API와 데이터는 영향을 받지 않는다.
