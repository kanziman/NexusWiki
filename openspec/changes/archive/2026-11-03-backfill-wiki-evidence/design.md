## Context

동기와 확정 요구사항은 proposal.md와 delta spec을 따른다. 2026-11-03 네 계획 게이트가 승인됐고 사용자가 로컬 구현 apply를 명시적으로 요청했다. 운영 적용 권한은 부여되지 않았다.

읽기 전용 집계에서 대상 30페이지 모두 기존 출처 청크가 있고 페이지당 3~11개, 전체 167개 후보 쌍이다. 28페이지가 검증 완료다. 일반 재컴파일은 지문 단락으로 생략될 수 있고 shadow에서 본문이 바뀔 수 있어 백필 경로로 사용하지 않는다.

## Goals / Non-Goals

**Goals:** 기존 본문을 읽으며 근거 연결만 사람이 확정할 수 있게 한다. 보고서와 적용은 분리하고, 낡은 검토 결과·교차 테넌트·중복을 차단한다.

**Non-Goals:** 본문 생성·재컴파일, 검증 상태·검색 색인 변경, 모든 페이지를 연결됐다고 만드는 목표, 근거의 주장별 완전성 인증, 4c, 에이전트의 운영 DB 쓰기.

## Decisions

### D1. 아키텍처 비교와 선택

| 기준 | A. 로컬 후보 보고서·수동 검토 (권고) | B. LLM 보조 후보 보고서·수동 검토 | C. 웹 검토 화면·워커 적용 잡 |
| --- | --- | --- | --- |
| 데이터 구조 | 버전·내용 해시가 있는 로컬 후보/승인 파일, 기존 근거 테이블 | A에 모델 판정·호출 기록 추가 | 후보·검토 상태용 DB 구조와 기존 근거 테이블 |
| API 영향 | 사용자 API 추가 없음 | 사용자 API 추가 없음, 공급자 호출 경로 필요 | 역할별 후보 조회·승인 API 필요 |
| 상태 관리 | 보고서와 승인 파일을 고정하고 적용 시 원본 재검증 | A에 모델 실패·재시도·비용 상태 추가 | DB 검토 상태와 at-least-once 잡 상태 관리 |
| 핵심 동작 | 기존 출처 청크를 전부 제시하고 어휘 점수로 정렬, 사람이 연결 확정 | 모델이 관련 청크와 이유를 제안, 사람이 연결 확정 | 멤버 화면에서 비교·승인하고 워커가 근거만 추가 |
| 구성 요소 | 워커 관리용 CLI, 보고서 생성기, 검토 입력 검증기, 원자적 추가 경계 | A와 모델 프롬프트·게이트웨이·비용 정책 | 후보 생성기, 화면·API, 승인 RPC, 워커 핸들러 |
| 기존 패턴 일치 | 워커 전용 쓰기·관리용 도구·기존 근거 테이블 재사용 | 게이트웨이 재사용 가능하나 분석에도 비용·공급자 의존 | 기존 위키 제안 승인 패턴과 일치하나 백필용 상태가 늘어남 |
| 테스트 용이성 | 결정적 파일 출력, 무쓰기·내용 보존·해시 경합을 로컬 DB로 검증 | A와 별도로 모델 오선정·위조 근거·비용·재시도 검증 | UI·API 역할·큐·DB 전체 경로 검증 필요 |

**선택 A (2026-11-03 사용자 승인):** 대상이 167쌍으로 작고 모두 기존 출처 안에 있어 사람 검토가 가능하다. 모델 비용·오선정과 상시 운영 UI를 추가하지 않고도 승인 요구사항을 충족한다. 점수는 표시 순서일 뿐 자동 승인 기준이 아니다. 관련 청크가 없으면 미확정으로 남긴다.

### D2. 경계와 불변 조건

- 읽기 전용 보고서 생성은 workspace를 명시하고 전체 페이지를 페이지네이션해 순회한다. 보고서에는 페이지와 후보 청크를 대조할 수 있는 내용을 담으며 운영 본문을 포함하므로 로컬 민감 자료로 취급하고 git에 넣지 않는다.
- 검토 결과는 후보 파일 해시와 승인한 페이지·청크 식별자를 연결한다. 승인되지 않은 쌍을 임의로 덧붙이지 못하게 파일·범위·대조 해시를 검사한다. 로컬 승인 파일은 암호학적 권한 증명 대신 운영자가 검토한 입력이다.
- 페이지 본문·메타데이터·출처와 청크 본문·좌표·원문을 검토 당시 해시로 고정한다. DB 적용 경계에서 최신 상태와 같은지 확인하고 잠금과 삽입을 한 트랜잭션으로 수행한다. CLI에서 사전 조회한 뒤 별도 INSERT하는 방식은 경합에 취약하므로 피한다.
- 기존 `replace_wiki_page_evidence`는 DELETE를 수행하므로 백필 적용에 사용하지 않는다. 추가 전용 worker RPC와 새 마이그레이션을 추가하고 아래 원자성·권한·배치 계약을 따른다.
- 보고서는 dry-run이 기본이고 모델 호출·사용량 기록·잡 생성도 없다. 적용은 별도 명령과 명시적 운영자 확인을 요구한다. 에이전트는 로컬 검증까지만 수행한다.

### D3. CLI와 로컬 검토 파일

도구는 `apps/worker/src/worker/evidence_backfill.py`, 진입점은 `python -m worker.evidence_backfill`이다. 제품 API·UI·잡은 추가하지 않는다. 기존 HTTP/PostgREST 워커 경계를 사용하며 이 도구에 필요한 설정은 Supabase URL과 service key뿐이다. 원문이나 키를 CLI 인자로 받거나 로그에 출력하지 않는다.

`export --workspace-id <uuid> --output-dir <경로>`는 읽기 전용 기본 동작이다. service-role 전용 읽기 RPC로 UUID 커서와 최대 50페이지 단위로 전체를 순회한다. 페이지·후보 0건도 명시적으로 보고하고 PostgREST 행 제한 때문에 일부 결과가 잘린 것을 성공으로 처리하지 않는다. 페이지의 기존 출처에 포함된 동일 workspace 청크만 후보로 낸다. 원문 본문과 청크 좌표가 맞지 않는 경우는 진단하고 확정 후보에서 제외한다.

후보 점수는 기존 core 정규화·bigram 기반 결정적 어휘 점수다. 0점도 숨기지 않고 동점은 식별자로 정렬한다. 자동 승인·모델 호출·임베딩·사용량 기록은 없다.

출력은 세 파일이다. 기존 파일은 기본적으로 덮어쓰지 않는다. 저장소 내부 출력은 gitignore할 `.local/evidence-backfill/`만 허용하고 다른 내부 경로는 거부한다. 보고서는 운영 본문을 포함하므로 로컬 민감 자료다.

| 파일 | 내용과 역할 |
| --- | --- |
| `candidates.json` | schema version·workspace·생성 시각·도구 버전, 페이지와 모든 후보의 식별자·대조 본문·원문·좌표·스냅샷 토큰·기존 연결·점수 |
| `review.html` | JSON 기반 정적 대조 보고서. 페이지와 후보를 비교하고 기존 연결·미확정 페이지를 표시. HTML escape하고 스크립트·외부 리소스·네트워크 호출 없음 |
| `approvals.json` | 후보 파일 원본 바이트 SHA-256·workspace·schema version과 승인한 페이지/원문/청크 쌍 목록. 처음에는 빈 목록이며 운영자가 검토 후 편집 |

`validate --candidates <파일> --approvals <파일>`는 로컬 파일만 읽는다. 파일 해시·schema·workspace·필수 토큰·중복·후보 목록 포함 여부를 검증한다. 승인 0건은 유효한 무작업이다. 오류는 안전한 코드와 행 번호로 보고하고 원문·자격증명을 싣지 않는다. 승인 파일은 신뢰된 운영자의 입력이며 암호학적 권한 증명이 아니다. 실제 권한과 사람 검토가 신뢰 경계다.

### D4. DB 토큰과 추가 전용 적용

새 마이그레이션 `0035_wiki_evidence_backfill.sql`을 계획하며 구현 시 최신 최대 번호를 다시 확인한다. 새 테이블 없이 읽기 전용 후보 RPC, 추가 전용 적용 RPC, 필요한 토큰 helper를 둔다. `security invoker`와 스키마 한정 참조를 사용한다. `public`·`anon`·`authenticated` 실행 권한을 회수하고 `service_role`만 실행한다. 사용자 요청 경로에는 특권 클라이언트를 추가하지 않는다.

토큰 계산은 DB의 같은 helper를 export와 apply가 재사용한다. 고정된 JSON 표현의 UTF-8 SHA-256이다. 페이지는 전체 저장 컬럼을 포함하고, 원문은 ID·본문·출처를 규정하는 저장 컬럼을 포함한다. 청크는 ID·workspace·원문·본문·좌표·순번을 포함한다. 원문·청크의 벡터·검색 파생 컬럼은 제외해 임베딩만 갱신됐다고 검토가 무효가 되지 않게 한다.

`apply --candidates <파일> --approvals <파일> --confirm-workspace-id <uuid>`는 운영자가 별도로 실행한다. CLI는 파일을 validate하고 접속 대상·workspace·승인 건수·후보 해시를 본문 없이 표시한다. 확인 workspace가 일치해야 진행한다. 다른 환경 파일 자동 탐색이나 원격 실패 시 로컬 전환은 없다. 승인 0건이면 RPC를 부르지 않는다.

적용 RPC는 한 workspace의 최대 500개 고유 승인 쌍을 한 트랜잭션으로 처리한다. 현재 167쌍은 한 배치다. 한도 초과는 자동 분할하지 않고 거부해 운영자가 검토 단위를 다시 나누게 한다. 배치의 순서는 다음과 같다.

1. schema·개수·중복·필수 인자와 모든 ID 실존을 검사한다. 없는 행이 JOIN에서 조용히 사라져 부분 성공으로 보이지 않게 한다.
2. 관련 원문 → 페이지 → 청크 순서, 각 UUID 오름차순으로 `for share` 잠금을 잡는다. 검증과 삽입이 끝날 때까지 변경·삭제를 차단한다. 잠금 제한·교착은 전체 배치 실패로 반환하고 자동 우회하지 않는다.
3. 잠금 후 동일 workspace·페이지의 현재 문서 출처·청크 소속·원문 좌표를 확인한다. 원문을 좌표로 자른 내용이 청크 본문과 같아야 한다. 토큰을 재계산해 검토 당시 값과 비교한다.
4. 하나라도 없거나 변경됐거나 범위가 틀리면 전부 거부한다. 정상 배치는 `wiki_page_evidence`에만 `insert ... on conflict do nothing`한다. 페이지·원문·청크·색인·개정·제안·잡·사용량에 쓰지 않는다.
5. 요청·신규·기존 연결 건수와 실제 신규 삽입된 쌍 목록을 반환한다. CLI는 후보·승인 해시와 결과를 로컬 `apply-result.json`에 저장한다. 결과 파일 저장 실패를 DB 롤백으로 오보고하지 않는다.

재실행은 토큰이 같으면 신규 0건으로 끝난다. 성공 후 페이지가 바뀌었다면 같은 파일도 stale로 거부하고 재검토한다. export의 여러 페이지가 workspace 전체의 동일 시점 스냅샷이라고 주장하지 않는다. 최신성은 적용 트랜잭션에서 보장한다.

### D5. 미확정·실패·복구

보고서는 후보 없음·승인 없음·기존 연결 있음·새 연결 추가를 구분한다. 연결률은 주장별 완전성 인증이 아니고 30/30을 목표로 하지 않는다. 근거가 부족하면 비워 두는 것이 정상 결과다.

검증 실패는 배치 전체가 자동 롤백된다. 성공 후 잘못 검토한 연결을 발견하면 결과의 실제 신규 삽입 목록을 기준으로 별도 제거 계획을 검토한다. 이 도구에는 자동 전체 삭제나 원복 명령을 두지 않으며 기존 근거를 되돌림 명목으로 지우지 않는다.

### D6. 검증 계획

- 파일·순수 로직: 결정적 정렬·0점 보존·Unicode 좌표·HTML escape·덮어쓰기 거부·승인 해시 변조·후보 추가·중복·workspace 불일치·빈 승인·본문 로그 비노출.
- 실제 로컬 DB: 교차 테넌트·출처 밖·미존재 ID 거부, 페이지·원문·청크 변경 후 stale 거부, 반복 적용·기존 근거 보존·한 쌍 실패 시 전체 롤백·요청/결과 건수 검증.
- 동시성: 페이지 수정·청크 재처리·원문 삭제와 경합해도 유효한 검토대로 추가하거나 배치 실패만 허용한다. 전후 페이지·검증·검색 색인·개정·제안·잡·사용량 불변을 확인한다.
- 권한: anon·authenticated RPC 거부, service-role 명시 workspace 범위와 복합 FK 검증, SEC-03·Ruff 유지.
- 수집 규모: 페이지 수가 조회 한도를 넘는 경우에도 전수 순회하거나 명시적 실패하며 조용한 누락을 허용하지 않는다.

## Risks / Trade-offs

- 어휘 유사성은 사실적 뒷받침을 보장하지 않음 → 사람 검토와 미확정 결과를 허용한다.
- 검토 후 페이지·청크 수정 → DB 경계에서 해시와 범위 검증을 원자적으로 수행한다.
- 보고서에 운영 본문 포함 → 로컬 전용 출력·커밋 제외·본문 없는 요약 로그를 사용한다.
- 기존 표의 연결률은 주장별 완전성 지표가 아님 → 목표를 30/30으로 두지 않는다.

## Migration Plan

1. 최종 설계·수직 슬라이스 승인 후 사용자의 명시적 구현 apply 요청을 받아 도구·0035·로컬 검증을 작성한다.
2. 두 리뷰 게이트와 필수 검증을 통과하고 PR 초안을 승인받는다. 추가 RPC는 이전 운영 코드와 호환된다.
3. 운영자가 0035를 선적용하고 linked 원장으로 확인한다. 에이전트는 실행하지 않는다.
4. 운영자가 워커 권한 경계의 도구로 export·보고서 검토·승인 파일 편집을 수행한다. 에이전트의 원격 읽기 전용 export는 별도 범위 확인 후 가능하다.
5. 운영자가 apply를 실행하고 신규 연결 목록과 품질 집계를 확인한다. 에이전트는 운영 apply나 머지를 실행하지 않는다.
