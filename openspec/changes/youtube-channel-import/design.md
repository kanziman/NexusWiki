## Context

동기는 `proposal.md`의 「Why」를, 계약은 `specs/youtube-channel-import/spec.md`를 본다. 이 설계를 가르는 제약은 셋이다.

1. **공식 API로는 타인 채널의 자막을 받을 수 없다.** `captions.download`는 영상 소유자 OAuth를 요구한다. 따라서 자막 획득은 비공식 경로에 의존할 수밖에 없고, 그 경로는 언제든 막힐 수 있다.
2. **`search.list`만 비싸다.** 호출당 100유닛, 일일 한도 10,000유닛. `channels.list`·`playlistItems.list`는 1유닛이라 영상 목록 조회는 사실상 공짜다.
3. **`raw_sources.source_type`에 `transcript`가 이미 있다.** `0001_core_schema.sql:97`의 check와 `SourceType.TRANSCRIPT`가 모두 존재하지만 아직 쓰이지 않는다 — 스키마 설계 당시 예정된 자리다.

## Goals / Non-Goals

**Goals:**

- 자막 공급자가 막혔을 때 **스펙과 태스크를 바꾸지 않고** 구현체만 교체할 수 있게 한다.
- 채널 검색 쿼터를 반복 검색에서 소비하지 않는다.
- 영상 한 편의 자막 실패가 같은 배치의 나머지를 막지 않는다.

**Non-Goals:**

- **새 워크스페이스 생성·타 워크스페이스로 저장.** Gate 1에서 전용 페이지 방식을 택하면서 저장 대상은 항상 현재 워크스페이스로 고정했다. 다른 워크스페이스에 수집하려면 그쪽으로 전환한 뒤 수집한다.
- **워크스페이스별 YouTube BYOK.** 공용 키로 시작한다. 쿼터 소진이 실제 문제가 된 뒤에 별도 change로 다룬다 — 지금 넣으면 `workspaces.custom_api_key`를 provider 구분이 가능한 구조로 일반화하는 마이그레이션이 따라붙는데, 그 비용을 정당화할 사용량 근거가 아직 없다.
- **자막 없는 영상의 오디오 전사(STT) 폴백.** 영상당 비용·시간이 크고, 다운로드 단계에서 자막 경로와 같은 IP 차단 문제를 그대로 만난다.
- **채널 구독과 신규 영상 자동 동기화.** 이번 범위는 사용자가 명시적으로 고른 영상의 1회성 수집이다.
- **재생목록 단위 수집**과 **조회수·길이 기반 자동 추천.** 선택은 전적으로 사람이 한다.
- **자막 언어 선택 UI.** 우선순위 규칙으로 자동 선택한다.

## Decisions

### D1. 선택 영상은 `transcript` source_type으로 등록하고 자막 추출은 워커의 parse 분기에서 한다

각 영상은 `source_type='transcript'`, `content=""`(sentinel), `metadata={video_id, channel_id, url}`인 `raw_sources` 한 행이 된다. URL 소스와 동일하게 등록 시점에는 외부를 건드리지 않고, `parse` 핸들러의 새 `transcript` 분기가 자막 어댑터를 호출해 본문을 채운다. 그 뒤 `compile → link_sync → embed`는 기존 그대로다.

중복 판정 키는 **정규화된 영상 URL의 해시**다(`https://www.youtube.com/watch?v=<id>`). 자막 본문이 아니라 영상 신원으로 잡아야, 자막이 나중에 수정돼도 같은 영상이 두 번 수집되지 않는다.

**기각한 대안**

- **URL source_type 재사용**: `parse`의 URL 분기 안에서 유튜브를 재분기하는 형태. 마이그레이션이 필요 없다는 이점이 `transcript` 값의 선존재로 사라졌고, 남는 것은 "URL 소스는 `fetch_source`의 SSRF 가드를 거쳐 읽는다"는 불변식에 조건부 예외를 파는 비용뿐이다. sources 목록에서 일반 웹페이지와 구분할 수단도 없다.
- **요청 시점에 자막을 받아 TEXT로 등록**: 워커를 안 건드리고 자막 없는 영상을 등록 전에 걸러낼 수 있다. 그러나 `sources.py`가 URL 페치를 워커로 미룬 이유(ING-01: 외부 서버의 응답 시간이 곧 이 API의 응답 시간이 된다)를 정면으로 위반한다. 영상 20편이면 요청 하나가 외부 왕복 20회에 인질이 되고 202 즉시 응답 계약이 깨진다.

### D2. 자막 획득은 `TranscriptProvider` 어댑터 뒤에 둔다

워커에 단일 진입점(`fetch_transcript(video_id) -> 자막 본문 | 구분 가능한 실패`)을 두고 구현체를 교체 가능하게 한다. 첫 구현은 무료 라이브러리로 하되, **스펙과 태스크 어디에도 공급자 이름이 등장하지 않는다** — 계약은 "자막을 얻거나, 구분 가능한 사유로 실패한다"까지다.

실패 사유는 최소 셋을 구분한다: 자막 없음 / 영상 접근 불가(비공개·삭제) / 공급자 일시 장애. 앞의 둘은 재시도해도 소용없고 마지막은 기존 잡 재시도로 해결되므로, 이 구분이 없으면 자막 없는 영상이 `max_attempts`까지 헛돌게 된다.

**기각한 대안**: 유료 자막 API를 처음부터 전제. 안정적이지만 월 구독비가 붙고, 어댑터가 있으면 막힌 뒤에 옮겨도 늦지 않다.

### D3. 채널 검색 캐시는 API 프로세스 메모리에 TTL로 둔다

`(질의, regionCode, pageToken)` 키로 응답을 캐시한다. 캐시가 API 쪽에 있으므로 반복 검색은 외부 호출뿐 아니라 D5의 내부 홉까지 건너뛴다.

**기각한 대안**: 캐시 테이블. 이 데이터는 테넌트 데이터가 아니라 외부 API 응답이라 `workspace_id`로 격리할 것이 없는데, RLS 하에서 사용자 경로가 읽고 쓰려면 `authenticated`에게 공유 테이블 INSERT 권한을 줘야 한다 — 임의의 멤버가 캐시를 오염시킬 수 있는 표면이 생긴다. `service_client`로 쓰는 것은 "사용자 요청 경로에 `service_role` 금지"라는 불변 규칙 위반이다. 메모리 캐시는 이 둘을 모두 피한다.

**대가**: 캐시가 인스턴스에 갇히고 재배포 때 사라진다. 최악의 경우가 "지금과 동일하게 검색 1회에 100유닛"이라 감수한다. API가 다중 인스턴스로 늘어나면 그때 공유 저장소로 옮긴다.

### D4. 영상 목록은 `search.list`가 아니라 `playlistItems.list`로 읽는다

`channels.list`로 채널의 uploads 재생목록 ID를 얻고(1유닛), `playlistItems.list`로 50개씩 페이징한다(1유닛). `search.list`에 `channelId`를 넘기는 방법도 있지만 그것은 호출당 100유닛이라, 영상 목록을 몇 페이지만 넘겨도 일일 쿼터가 녹는다.

### D5. YouTube API 키는 워커가 소유하고 API는 내부 엔드포인트로 프록시한다

`ApiSettings`에는 provider 자격증명을 담을 필드를 둘 수 없다. api와 worker가 단일 이미지를 공유해 api 프로세스가 worker 모듈을 물리적으로 import 할 수 있으므로, 격리는 오직 **"키를 담을 필드가 없다"**로만 성립한다(`apps/api/src/api/settings.py`의 SEC-01 주석, `packages/core/tests/test_settings.py`의 허용 목록 단언).

이 저장소는 같은 문제를 이미 두 번 풀었다 — 임베딩(`QUERY_EMBEDDING_INTERNAL_*`)과 LLM 스트리밍(`LLM_STREAM_INTERNAL_*`)이 모두 **워커가 provider 키를 들고 내부 리스너를 노출하고, API는 내부 호출자 토큰으로 프록시하는** 형태다. 채널 검색도 같은 형태를 따른다.

- 워커: `YOUTUBE_API_KEY`를 소유하고 채널 검색·영상 목록 내부 리스너를 노출한다.
- API: `YOUTUBE_SEARCH_INTERNAL_URL` · `_TOKEN` · `_TIMEOUT_SECONDS`만 갖는다. 이 토큰은 provider 자격증명이 아니라 내부 호출자 자격이며, `test_settings.py`의 허용 목록에 근거와 함께 등록한다.

**기각한 대안**: 대시보드(Next.js 서버)가 YouTube를 직접 호출. FastAPI를 경유하지 않아 SEC-01과 무관해지지만, provider 키가 세 번째 프로세스로 퍼지고 서버리스 인스턴스가 자주 교체돼 D3의 메모리 캐시 전제가 무너진다.

## Risks / Trade-offs

- **자막 공급자가 Railway의 데이터센터 IP를 차단한다** → 이 설계에서 가장 현실적인 실패 시나리오다. D2의 어댑터가 유일한 방어선이므로, 첫 슬라이스부터 어댑터 경계를 지키고 실패 사유를 관측 가능하게 남긴다. 차단이 확인되면 프록시 또는 유료 API로 구현체만 교체한다.
- **공용 쿼터를 한 사용자가 소진해 전체 검색이 멈춘다** → 캐싱으로 반복 검색을 지우고, 소진 시 "결과 0건"이 아니라 구분 가능한 사유를 내려 사용자가 상황을 이해하게 한다(스펙 요구사항 3). 워크스페이스별 BYOK는 이 문제가 실측될 때 다룬다.
- **영상 20편 일괄 선택이 크레딧을 한 번에 태운다** → 등록은 건별 예산 프리플라이트를 그대로 통과하므로 상한에 닿는 순간부터 거부된다. 이미 만들어진 `raw_sources` 행은 남고(기존 계약), 사용자는 기존 402 → `CreditLimitModal` 경로를 본다.
- **자막의 시간축 정보를 버린다** → 본문을 평문으로 이어붙이면 "몇 분 지점"으로 되돌아갈 수 없다. 이번 범위는 기존 청크 좌표(char 구간)와의 일관성을 우선한다. 타임코드 인용은 후속 change의 몫이다.

## Migration Plan

DB 마이그레이션이 없다. `transcript`는 이미 허용된 값이고 새 테이블도 만들지 않는다.

배포 순서는 워커 먼저다 — 이유가 둘이다. (1) 대시보드가 먼저 나가면 사용자가 등록한 `transcript` 소스를 구버전 워커가 `unsupported_source_type`으로 죽인다. (2) D5의 내부 검색 리스너가 없으면 API의 검색 프록시가 갈 곳이 없다. 롤백도 역순(대시보드 먼저 내림)이며, 이미 등록된 `transcript` 행은 워커가 복구되면 기존 재시도 경로로 처리된다.

## Open Questions

- **자막 언어 우선순위.** 한국어 수동 자막 → 한국어 자동생성 → 영어 순으로 볼 것인지, 채널의 기본 언어를 먼저 볼 것인지. 어느 쪽이든 스펙의 요구사항과 슬라이스 구성이 바뀌지 않아 구현 중 정한다.
- **캐시 TTL 길이.** 채널 검색 결과는 빠르게 변하지 않아 몇 시간에서 하루 사이면 되고, 값 자체는 계약에 영향이 없다.
