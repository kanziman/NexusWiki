# v1.1 Discovery Backlog — Dashboard and Ingestion

**Captured:** 2026-08-13

This document records observed product issues and requested improvements before v1.1 scope is finalized. It is a discovery backlog, not an approved implementation plan. Priorities describe current product impact and must be revalidated when the milestone is planned.

## Priority 0 — Broken access and blocked interactions

### 1. Korean wiki slugs render “page not found”

**Observed behavior:** Four wiki pages whose slugs include Hangul render “페이지를 찾을 수 없습니다”; the ASCII-only slug `hmg-sso` renders correctly.

**Evidence already collected:**

- All five `wiki_pages` rows are present, uniquely scoped to the expected workspace, and stored in NFC.
- The stored UTF-8 bytes for Hangul slugs match the browser URL's percent-encoded bytes.
- A direct PostgREST query using the same JWT and `workspace_id + slug` equality filters returns the correct row.
- An authenticated browser request reaches the server with a correctly percent-encoded path and receives HTTP 200, but the rendered page is the not-found state.
- Middleware only checks authentication; it does not rewrite or redirect wiki paths.
- The route is dynamic (`ƒ`), so this is not a static stale-404 cache issue.

**Working hypothesis:** In the deployed Next.js App Router path, `[slug]` can arrive percent-encoded rather than decoded for non-ASCII dynamic segments. `apps/dashboard/app/w/[workspaceId]/wiki/[slug]/page.tsx` uses the parameter directly in `.eq("slug", slug)`, causing a literal percent-encoded string not to match the NFC database value.

**Candidate fix:** Safely decode the route slug before querying. Guard malformed percent encodings so a bad URL remains a not-found result rather than a server error.

**Acceptance criteria:** Authenticated navigation works for ASCII, Hangul-only, and mixed ASCII/Hangul slugs; malformed encoded paths do not produce a 500; regression tests cover encoded and already-decoded inputs.

### 2. File dropzone cannot be opened by click

**Observed behavior:** Drag and drop works in Sources, but clicking the dropzone does not open the OS file picker.

**Likely cause:** The visual drop target has drag handlers but no click/keyboard activation tied to its hidden file input.

**Scope:** Make the target activate the existing labelled file input on click, `Enter`, and `Space`; retain drag/drop, existing upload API calls, and accessible file-input label.

**Acceptance criteria:** Mouse click, keyboard `Enter`, keyboard `Space`, and drag/drop all select a file; duplicate picker opening is avoided; existing submission and error tests still pass.

### 2.1 Add multiple-file source upload with filename-derived titles

**Product requirement:** Let users select or drop multiple supported files at once. Each file must become an independent source and independent processing chain, so one duplicate or failed file does not block the rest.

**Title behavior:** Do not show a single shared title field in multiple-file mode. Derive each source title from its filename with the extension removed; preserve Unicode/Hangul titles. Present per-file queued, duplicate, uploading, processing, completed, and failed states.

**Critical dependency:** Complete **#1 Korean wiki slug retrieval** before enabling filename-derived titles for multiple upload. The existing slug generator deliberately supports Hangul (`가-힣`), so a filename such as `IVI 대시보드 요구사항.pdf` can produce a valid Hangul-containing title and slug. However, the current route lookup bug makes those generated wiki pages inaccessible. Do not make bulk upload generate user-facing Hangul slugs until encoded and already-decoded slug lookup is verified end to end.

**Implementation boundary:** Keep the existing single-file raw-byte upload endpoint as the per-file operation unless a separately designed batch contract proves necessary. The client may schedule bounded concurrent requests, but must preserve the current per-source MIME validation, size limit, Storage ordering, deduplication, RLS, and individual job lifecycle.

**Acceptance criteria:** Multiple supported files can be selected or dropped; no shared title field is shown in that mode; each file reports its own outcome; a partial failure does not cancel successful files; Hangul filename → title → slug → wiki navigation is covered by end-to-end regression after #1 is fixed.

## Priority 1 — Navigation, account clarity, and first-use flow

### 3. Support a user-to-many-project entry flow

**Product requirement:** One user can belong to many projects/workspaces. After login, the user must be able to see their accessible projects, choose one, and enter that project's wiki without crossing tenant boundaries.

**Requested flow:**

1. Login resolves the requesting user's RLS-scoped workspace list.
2. If exactly one workspace is available, redirect directly to its workspace home.
3. If multiple workspaces are available, show a project-selection screen or an equivalent explicit chooser before entering a workspace.
4. Selecting a project enters its workspace home, from which Sources, Ask, Wiki, Graph, and Settings remain scoped by the URL workspace ID.
5. The header workspace switcher remains available after entry for switching among accessible projects.

**Security boundary:** The list must come exclusively from the requester's RLS-scoped query. Never reveal names, IDs, counts, or existence of projects the user cannot access. The target workspace layout continues to redirect inaccessible IDs without distinguishing “not found” from “not a member.”

**Acceptance criteria:** A user with multiple memberships can choose and switch projects; each project shows only its own sources, questions, and wiki pages; a tampered workspace URL cannot expose another project's data; a user with zero memberships receives the existing invitation guidance.

### 4. Direct the root route into the appropriate workspace flow

**Observed behavior:** A user who has workspace membership lands on `/` and sees “워크스페이스가 없습니다 — 관리자에게 초대를 요청하세요.”

**Requested behavior:** Instead of that message, use the multi-project entry flow above: redirect a user with exactly one membership to its workspace home, and show the project selector when the user has multiple memberships.

**Boundary:** Keep the no-membership message for users who genuinely have zero accessible workspaces. Preserve the existing RLS boundary and avoid disclosing inaccessible workspace existence.

**Open decision:** Use a deterministic workspace ordering (for example the existing name ordering) until a last-visited workspace preference exists.

### 5. Expose authenticated account state and logout

**Observed behavior:** The dashboard header does not make it clear that the user is signed in and has no visible logout path.

**Scope:** Add an account affordance in the header that identifies the current session without exposing unnecessary profile data, and a clear logout action.

**Acceptance criteria:** A signed-in user can identify their session, sign out, reach `/login`, and no longer access protected workspace routes. Keyboard and mobile access remain usable.

### 6. Replace the workspace-home placeholder with an actual dashboard

**Current implementation:** `apps/dashboard/app/w/[workspaceId]/page.tsx` exists only to establish the route segment and renders placeholder copy.

**Requested outcome:** A workspace landing page that makes the next action obvious: add a source, ask a question, or browse/manage wiki content.

**Scope boundary:** Reuse existing Sources, Ask, and Wiki surfaces and their access controls first. Do not create new backend data models merely to fill the homepage.

**Design direction:** Retain the quiet editorial visual system while giving the page a meaningful first-use and returning-user state.

**Recommended first version:**

- a workspace name and a short, useful status summary;
- two primary next actions: `자료 추가` and `질문하기`;
- a recent-activity area that shows recent sources with processing state and recently created or updated wiki pages;
- a focused empty state that guides a new workspace toward adding its first source.

**Deliberate exclusions for the first version:** Keep graph exploration, detailed operational metrics, and complex analytics in their existing dedicated screens. Do not turn the homepage into a second Operations dashboard.

**Open design work:** Confirm the exact layout, loading/empty states, and the smallest existing RLS-scoped queries needed to supply the summary and activity lists.

### 6.1 Add Google OAuth as a login/signup option

**Observed behavior:** `/login` supports email/password only (Supabase Auth). There is no social sign-in option.

**Requested behavior:** Add a "Google로 계속하기" action on the login/signup surface using Supabase Auth's Google OAuth provider.

**Dependencies and scope:**

- Requires a Google Cloud OAuth 2.0 client (authorized redirect URI = the Supabase project's `/auth/v1/callback`); the client ID/secret are external, user-provided credentials, not something to generate in-repo.
- Requires enabling the Google provider in Supabase Auth config — locally via `[auth.external.google]` in `supabase/config.toml`, and in the cloud project via Supabase Studio's Auth Providers settings (secrets are not committed to the repo, consistent with existing `.env` handling).
- A Google sign-in creates a fresh `auth.users` row exactly like existing email/password signup, so it interacts with the existing invite-only workspace model: confirm a newly Google-authenticated user with no workspace membership correctly falls into the existing "no workspace yet" / invitation guidance (see #3), rather than bypassing it.

**Acceptance criteria:** A user can sign in with a Google-linked account; a brand-new Google sign-in follows the same no-workspace guidance as email/password signup; existing JWT/RLS session handling is unaffected; the button fits the existing quiet editorial login page visually.

## Priority 2 — Sources workflow and UI consistency

### 7. Make source processing status compact and actionable

**Observed behavior:** `sources_page.png` shows all five pipeline stages as a permanently expanded vertical sequence under every source. It is informative but consumes substantial list space and makes active work hard to scan.

**Requested UX:**

- Default to a one-line current summary such as `파싱 중 · 2/5 단계` with a progress indicator.
- Keep the active stage prominent and collapse completed stages.
- Show error detail and retry only for failed work.
- Render completed items as a compact completion summary rather than five repeated checkmarks.
- Preserve the real five-stage model, polling lifecycle, retry, cancel, and accessible status semantics.

### 8. Stabilize navigation item geometry across active routes

**Observed behavior:** Switching between Sources, Ask, and other navigation routes moves items within the header.

**Likely cause:** Active-state border, padding, or font treatment changes the dimensions of a link.

**Scope:** Reserve identical vertical underline space and use consistent padding/line-height for every item; active state must not alter the x/y geometry of any navigation button.

**Acceptance criteria:** Route activation does not shift links or header height at desktop or narrow widths; active state remains visible without relying on color alone.

### 9. Audit and normalize unexpected dark border lines

**Reference images:** `image.png`, `image1.png`.

**Areas to inspect:**

- header lower divider;
- active-route underline;
- workspace-switcher outline;
- whether dark areas at screenshot edges are browser/capture chrome rather than application DOM;
- whether any line is using legacy strong black tokens instead of the quiet editorial rule color.

**Direction:** Use the light `--nw-rule` divider consistently for structural separation. Reserve near-black borders for focus or genuinely selected/active controls, and ensure those states also have non-color cues.

### 10. Make Ask prompt-template chips understandable and toggleable

**Observed behavior:** The chips above the Ask input are prompt-template selectors, but the UI does not explain their purpose. A template can be selected, but the user cannot clear that selection by clicking the selected chip again.

**Requested behavior:** Add the plain-language label `질문 템플릿` and helper copy `원하는 질문 방식을 선택하세요. 다시 누르면 선택이 해제됩니다.` above the chips. Treat templates as an optional, single-select toggle: clicking an unselected chip applies its prompt; clicking the selected chip clears the active template and restores the ordinary input state. Selecting a different chip switches templates directly.

**Copy decision:** Replace the awkward template name `실행 항목 추출` with `실행할 일 추출`. This keeps the original meaning while making the result and action clearer in Korean.

**Scope:** Preserve other template copy, Ask submission flow, and keyboard accessibility. The selection state must be exposed semantically (`aria-pressed` or an equivalent selected state), not by color alone.

**Acceptance criteria:** Users can identify the chips as question templates before choosing one; the selected template can be cleared with mouse and keyboard; only one template is active at a time; switching templates works; clearing does not discard user-entered question text unless that is an explicitly agreed product rule.

### 11. Improve Ask reading flow, citations, and composer hierarchy

**Reference:** `ask_page.png`.

**Observed behavior:**

- A long answer appears as a dense, nearly unbroken text wall. Markdown-like markers such as `##` and `---` are visible in the reading surface instead of providing clear document structure.
- Inline citation markers crowd the text and fragment line rhythm, especially in a Korean answer with many sources.
- Opening the citation panel consumes a large fixed portion of the viewport and competes visually with the answer rather than supporting it.
- The composer below the chips has a very weak visual boundary and no obvious primary send affordance in the captured state.

**Requested UX:**

- Render supported answer structure as readable headings, paragraphs, lists, and dividers while keeping untrusted content safe.
- Give citations a quieter inline treatment and reveal source detail on deliberate interaction; preserve keyboard access and the existing side-panel evidence model.
- Make the citation panel responsive: preserve a useful reading width, support closing, and become an overlay or bottom sheet at narrow widths.
- Present the composer as the next clear action with a descriptive placeholder and a visible send button; retain Enter/IME-safe submission behavior and existing SSE flow.

**Acceptance criteria:** Long Korean answers remain scannable; citations do not create horizontal overflow or obscure surrounding words; citation detail is reachable and dismissible; the composer and submit action are unmistakable at desktop and mobile widths; existing citation-security constraints and streaming behavior remain intact.

### 12. Make wiki pages traceable to their source material and easier to browse

**Reference:** `wiki_page.png`.

**Observed behavior:** The Wiki route presents a plain, unstructured list of page titles with little visual hierarchy or indication of page metadata. More importantly, a reader cannot see which raw source(s) support a wiki page or navigate back to the original uploaded material from the wiki experience.

**Product requirement:** A wiki must remain traceable to its evidence. Each page should make its supporting source material discoverable without exposing data outside the active workspace.

**Requested UX:**

- Turn the wiki list into a browsable library with page title, short supporting metadata, clear item affordance, useful empty/loading states, and responsive list behavior.
- On an individual wiki page, show a compact `출처` section that lists the raw source title/type and lets an authorized member open the corresponding source context.
- When a page is compiled from multiple source chunks, explain the relationship honestly: show the contributing source(s) and, where available, the relevant excerpt/anchor rather than implying one source owns every statement.
- Keep provenance secondary to the page content: a collapsible right rail on wide screens and a disclosure section on narrow screens are preferred over an always-dominant panel.

**Security boundary:** All source and page lookups remain scoped by workspace and requester RLS. Do not expose raw storage URLs, chunks, or sources belonging to another project. Preserve existing citation/anchor safety rules for excerpts and links.

**Acceptance criteria:** A workspace member can identify and open the source material supporting a wiki page; a page with multiple contributing sources communicates that clearly; users without workspace access learn nothing about source existence; the Wiki list and page detail remain readable at desktop and mobile widths.

### 13. Polish wiki detail rendering, verification state, and unresolved links

**Reference:** `wiki_detail.png`.

**Observed behavior:**

- Document Markdown is rendered as plain text: headings retain `##`, lists retain leading hyphens, and blockquotes retain `>` instead of becoming readable page structure.
- The verification line exposes an opaque UUID next to the status, which does not help a reader assess the page.
- The large pink `검증됨으로 표시` button competes with the document title and reads like a primary editing action, although the page says it is compiled and cannot be edited directly.
- Red unresolved-link/error text is visually abrupt and contains machine-like status wording (`아직 작성되지 않음 · 지금 생성`) inside running prose.
- The compiled-page notice, verification metadata, document body, and provenance need a clearer hierarchy.

**Requested UX:**

- Render the supported compiled Markdown subset into semantic headings, lists, paragraphs, dividers, and blockquotes, with safe handling for untrusted content.
- Replace the reader-facing UUID with useful verification metadata: status, date, and a human-readable explanation. Keep the opaque identifier only in a developer diagnostics view or a copyable secondary detail.
- Reframe verification as a compact status/disclosure action rather than the visually dominant action above the article. This is a human review acknowledgement, not automatic fact verification: replace `검증됨으로 표시` with `검토 완료로 표시`, and explain `원문을 확인한 뒤 이 페이지를 검토 완료로 표시합니다.` before the action. Keep any mutation restricted to authorized roles.
- Render unresolved wiki links as an intentional inline callout or compact action, with natural Korean product copy reviewed through `humanize-korean`; distinguish “not yet written” from a technical retrieval or permission error.
- Establish a stable detail layout: short compiled-page notice, title and metadata, readable article column, source/provenance rail, and responsive mobile disclosures.

**Additional information on the wiki page:** Add a compact `페이지 정보` disclosure with the compiled date, review status and reviewer/date when present, source count, and an explanation of the page lifecycle: `이 페이지는 등록한 원문을 바탕으로 생성됩니다. 원문이 바뀌면 내용도 다시 정리됩니다.` Link or disclose the supporting source list from the provenance requirement above. Do not show internal UUIDs in the ordinary reader view.

**Acceptance criteria:** Headings and lists are scannable without raw Markdown markers; verification is understandable without a UUID; unresolved links explain the next action without breaking sentence rhythm; source/provenance remains reachable; compiled-content and role/RLS constraints remain enforced.

### 14. Make the knowledge graph understandable and navigable

### 15. Clarify Settings structure, member state, and invitation feedback

**Reference:** `setting.png`.

**Observed behavior:** The settings page has two tabs (`멤버`, `운영 현황`) but no page-level context. The member list is shown as indistinguishable skeleton bars in the captured state. The invitation form carries disproportionate visual weight, and a generic red “invitation could not be sent” message gives the user no safe next step.

### 15.1 Correct misleading invite success message

**Observed behavior:** After a successful `invite_workspace_member` RPC call, `InviteForm.tsx` shows "초대를 보냈습니다" ("Invite sent"). No email or other notification is ever sent — the RPC only requires the invitee to already have a NexusWiki account (matched by email in `auth.users`) and directly inserts a `workspace_members` row. The invited person has no way to learn about the addition except noticing the new workspace on next login.

**Root cause:** No email-sending mechanism exists anywhere in the codebase (`apps/api`, `apps/worker`) or in Supabase Auth config — `[auth.email.smtp]` is commented out in `supabase/config.toml`. What the UI calls an "invite" is actually an immediate roster addition for an existing user, not an asynchronous email invitation.

**Requested fix (copy-only; no backend/RPC change in this item):** Replace "초대를 보냈습니다" with wording that matches actual behavior — e.g. "멤버로 추가했습니다" ("Added as a member") — reviewed through `humanize-korean`. Keep the existing helper copy (or add it) clarifying that the invitee must already have a NexusWiki account for this to succeed.

**Deferred, separate scope:** A real email-based invitation flow for people without an existing account is a larger feature (would need `auth.admin.inviteUserByEmail` or equivalent, plus SMTP/email provider setup) and is not part of this copy fix.

**Acceptance criteria:** Success message accurately reflects immediate roster addition rather than an email invitation; copy passes `humanize-korean` review; no functional or RPC changes.

### 15.2 Add invite-link (token) join flow for non-registered users

**Motivation:** `invite_workspace_member` requires the invitee to already have a NexusWiki account (`NW404` otherwise). Real email-based invitation via Supabase Auth's admin API was evaluated and set aside — it needs SMTP/email-provider integration, a new backend admin endpoint, and pending-invite state (see the "Deferred, separate scope" note in #15.1).

**Rejected alternative — searchable workspace directory:** Letting a user search for and request to join a workspace at signup was also considered and rejected. It directly conflicts with the existing security boundary in #3 ("Never reveal names, IDs, counts, or existence of projects the user cannot access") and still needs an owner-approval step, adding nearly as much complexity as email invites while weakening tenant privacy.

**Recommended direction — shareable invite link:** An owner generates a unique, workspace-scoped invite token (random string with expiry). The link is shared out-of-band (Slack, KakaoTalk, etc.) — no SMTP or admin API required. A recipient, whether or not they already have a NexusWiki account, opens the link, logs in or completes signup, and is added to the workspace as a member.

**Scope:**

- A new table (e.g. `workspace_invite_tokens`) with `workspace_id`, `token`, `role`, `created_by`, `expires_at`, `used_at`/`used_by`; RLS scoped so only workspace owners can create/list tokens for their own workspace.
- A redemption path: an authenticated user opening `/invite/{token}` resolves the token, validates it is not expired/already used, and inserts a `workspace_members` row for the current session's user — reusing the `SECURITY DEFINER` membership pattern established in 0004/0014.
- Signup flow must carry the token through an unauthenticated visit → Supabase Auth signup/login → immediate redemption, since the recipient may not have an account yet.
- UI: owner-side link generation/copy/revoke action in Settings → Members (next to the existing invite form from #15); recipient-side landing page with an explicit "이 워크스페이스에 참여합니다" confirmation before joining.

**Open decisions:** single-use vs. multi-use tokens, expiry duration, whether tokens are revocable, and whether this coexists with or replaces the existing "invite by email of an already-registered user" RPC.

**Acceptance criteria:** An owner can generate and share an invite link; a recipient without an existing account can sign up and land in the correct workspace via the link with no email/SMTP dependency; the link cannot be used to discover other workspaces or bypass RLS; expired or invalid tokens are rejected safely.

## Priority 2.5 — Developer retrieval observability

### 16. Add a developer-only hybrid-retrieval trace

**Goal:** Let an authorized developer understand why an Ask answer was produced, from query normalization through hybrid retrieval to final citations, without exposing sensitive retrieval payloads to ordinary users.

**Trace contents:**

- a `trace_id` for each Ask request;
- normalized query and selected question template;
- dense and lexical candidate chunk IDs, source/page titles, scores, and ranks;
- RRF combination result, final ordering, and explicit exclusion reason where available;
- citations selected for the answer;
- duration of query embedding, database retrieval, combination/reranking, and LLM streaming;
- no-evidence, budget, and individual-channel failure decisions.

**UI direction:** Expose trace lookup in a separately authorized developer/owner diagnostics surface, preferably as a `검색 추적` area in Settings/Operations. Do not place it in the standard Ask reading view. A development-only query flag may be useful for local iteration, but must not become an authorization bypass in production.

**Security boundary:** Preserve the existing Operations API rule that ordinary operational responses do not disclose source payload, `last_error`, usage metadata, or model/provider detail. Restrict trace access by role and environment; avoid full raw content by default, use IDs/title/safe short preview where necessary, and define retention plus masking for potentially sensitive user queries.

**Acceptance criteria:** An authorized developer can follow one Ask request end-to-end and explain the final citations/ranking; an unauthorized user cannot retrieve trace data or use a debug flag to bypass access control; trace collection has bounded retention and does not alter normal Ask latency or response semantics materially.

## Priority 3 — DOCX ingestion (independent deliverable)

### 17. Add DOCX source ingestion

**Current support:** Direct uploads accept PDF, plain text, and Markdown. DOCX is rejected at the API MIME allowlist before worker extraction.

**In scope:**

- accept the DOCX MIME type in the upload API;
- extract paragraphs and table cell text in `nexuswiki_core.extract`;
- feed extracted text through the existing parse → compile → link sync → embed job chain;
- distinguish unsupported/corrupt DOCX failures safely;
- show DOCX in user-facing supported-file guidance;
- add unit and route-level regression tests.

**Out of scope:** Embedded-image OCR, pixel-perfect layout recovery, PPTX, and XLSX.

**Acceptance criteria:** A valid DOCX is uploaded, processed, compiled into wiki output, and retrievable by Ask; a malformed DOCX reaches a safe, actionable failure state without exposing raw parser errors.
