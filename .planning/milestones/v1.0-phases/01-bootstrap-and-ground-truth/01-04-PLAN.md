    **`scripts/verify_auth_hardening.sh`** — `set -euo pipefail`. `.env.local`에서 `SUPABASE_URL`과
    `SUPABASE_PUBLISHABLE_KEY`를 읽고(없으면 그 키 이름을 지목하며 exit 1), 세 단언을 수행한다.
    모든 호출은 `apikey: $SUPABASE_PUBLISHABLE_KEY` 헤더와 `Content-Type: application/json`을 쓴다.
    스크립트는 어떤 경우에도 키 값이나 URL 전체를 stdout에 출력하지 않는다 — 판정 결과 문자열만 출력한다.

    1. **6자 비밀번호 가입 거부** — `POST $SUPABASE_URL/auth/v1/signup` 에 무작위 테스트 이메일과
       6자 비밀번호로 요청한다. HTTP 상태가 4xx여야 하고 응답 본문의 오류 코드가 약한 비밀번호를
       가리켜야 한다. 2xx가 오면 exit 1.
    2. **12자 이상 가입은 성공하되 확인 대기 상태** — 같은 엔드포인트에 16자 비밀번호로 요청한다.
       2xx여야 하고, 응답의 사용자 객체에 `email_confirmed_at`이 없거나 null이어야 한다.
       (여기서 만든 계정은 5단계에서 지운다.)
    3. **미확인 이메일 로그인 불가** — `POST $SUPABASE_URL/auth/v1/token?grant_type=password` 에
       2단계의 이메일/비밀번호로 요청한다. 4xx여야 하고 오류가 이메일 미확인을 가리켜야 한다.
       2xx로 토큰이 돌아오면 exit 1.
    4. 세 단언이 모두 통과하면 `auth_hardening: ok` 를 출력하고 exit 0.
    5. **정리** — 2단계에서 만든 테스트 계정을 Admin API
       (`DELETE $SUPABASE_URL/auth/v1/admin/users/<id>`, `apikey` 및 `Authorization: Bearer`에
       `SUPABASE_SECRET_KEY`)로 삭제한다. `SUPABASE_SECRET_KEY`는 이 정리 단계에서만 읽고,
       스크립트 어디에서도 출력하지 않는다. 정리는 `trap`으로 걸어 앞 단계가 실패해도 실행되게 한다.
       ⚠️ 이 스크립트는 개발자 머신 전용이다 — Railway `api` 서비스는 `SUPABASE_SECRET_KEY`를 갖지
       않으므로(금지사항 P1) 배포 환경에서 돌아가지 않는다. 주석에 명시한다.

    `docs/ops/auth-hardening-record.md` 에 검증 섹션을 추가한다 — 실행 일시, 세 단언 각각의 관측 HTTP

  </action>
