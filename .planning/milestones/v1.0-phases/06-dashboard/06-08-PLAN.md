  <action>
    No files change in this task — it records, in this PLAN.md, the Claude's-Discretion design
    call `06-CONTEXT.md` explicitly delegated for UI-06 (its Phase Boundary note says graph
    reads should "consume the depth<=2/fan-out-cap/cycle-guard RPC 05-CONTEXT.md already
    fixed"), so the deviation is auditable rather than silent:

    `GET /workspaces/{id}/graph` (`wiki_graph_neighborhood`) requires a `seed_wiki_id` and caps
    `total_limit` at 200 (query param `le=200`) — it answers "what's near this ONE node", not
    "show me the workspace's graph". UI-06's literal, binding requirement is the opposite shape:
    an overview with a category lens filter and EXPLICIT 1000-row-cap handling — a cap that only
    makes sense against PostgREST's blanket `max_rows=1000` (`supabase/config.toml:18`), which
    the neighborhood RPC's own independent 200-row cap already sits well under. Building the
    canvas around the RPC would either ignore the literal 1000-cap requirement (the RPC never
    gets near it) or require synthesizing a large view by calling the RPC repeatedly per node,
    which is not "consuming the RPC" so much as building a different traversal on top of it.

    This plan therefore builds the canvas on direct `wiki_pages`/`wiki_links` PostgREST reads
    (Task 2), which both satisfy the literal 1000-cap requirement AND remain within the same
    RLS-scoped, depth-bounded read architecture Phase 5 established (reading a table Phase 5's
    own migrations already gated by `wiki_pages_select_member`/`wiki_links_select_member` is
    still "consuming" that architecture, just not the one specific RPC). The neighborhood RPC
    is left uncalled by this phase — recorded as an `OPT-OUT` in `COVERAGE.md` — available for a
    future "explore from this node" interaction that is not part of UI-06's v1 scope.
  </action>
