고정할 계약 세 가지:

**멱등성 — 같은 잡을 두 번 처리** (SPEC Edge Coverage R10 idempotency): `noop` 잡을 인큐하고 루프를 한 번 돌려 `succeeded`가 되게 한다. 그다음 같은 `job_id`에 대해 핸들러 실행과 `complete_job` 호출을 **한 번 더** 수행한다. 상태가 여전히 `succeeded`로 수렴하고 예외가 나지 않는 것을 단언한다. 이것은 `complete_job`의 `where ... and status = 'running'` 절이 재호출을 0행 no-op으로 만들기 때문에 참이며(`0003_jobs.sql:145`), 그 절에 의존하고 있다는 사실을 테스트 주석에 남긴다.

**경합 — `release_job` 이후의 지연 완료** (SPEC Edge Coverage R10 concurrency): 워커 A(`worker_id='A'`)가 잡을 claim한다. A가 `release_job(job_id, 'A')`로 반납한다. 워커 B(`worker_id='B'`)가 같은 잡을 claim한다. 이제 A가 뒤늦게 `complete_job(job_id)`을 부른다. ⚠️ 여기서 잡이 `succeeded`가 되어버리면 B의 진행이 덮어써진다. `complete_job`은 `locked_by`를 보지 않으므로, 워커 루프가 **반납 이후 그 잡에 대한 완료 처리를 시도하지 않도록** 되어 있어야 한다. Task 2의 루프가 반납 후 해당 잡 참조를 버리는지 확인하고, 버리지 않는다면 고친다. 테스트는 루프의 이 행동을 단언한다 — SQL 함수가 아니라 워커 코드가 이 계약의 주체다.

**워크스페이스 스코프 전달**: 클레임한 잡의 `workspace_id`가 핸들러에 그대로 전달되는지 실제 잡으로 확인한다. `service_role`은 BYPASSRLS이므로 이 값이 핸들러에 닿지 않으면 Phase 3의 실제 핸들러가 교차 테넌트를 읽는다.
