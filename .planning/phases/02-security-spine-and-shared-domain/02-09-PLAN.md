`.github/workflows/ci.yml`을 만든다. 저장소 최초의 워크플로우다. 주석은 한국어로 쓴다.

트리거는 pull request다. 잡 네 개를 독립적으로 둔다 — 하나가 실패해도 나머지가 돌아야 어느 검사가 깨졌는지 한 번에 보인다:

1. **`pre-commit`** — Python(`.python-version`의 버전)과 Node/pnpm(`packageManager` 필드의 pnpm 버전)을 모두 세우고, `uv sync`로 dev 그룹을 설치한 뒤 `apps/dashboard`에 `pnpm install`을 돌리고 `pre-commit run --all-files`를 실행한다. `.pre-commit-config.yaml`의 prettier 훅이 `pnpm --dir apps/dashboard exec prettier`를 부르므로 Node 없이는 이 잡이 환경 문제로 실패한다
2. **`service-usage`** — `bash scripts/ci_check_service_usage.sh`를 돌리고, 추가로 `uv run ruff check apps packages`를 돌려 02-03-PLAN이 건 `TID251` banned-api 규칙이 실제로 걸리는지 함께 확인한다. 두 검사가 같은 것을 다른 각도에서 본다
3. **`bundle-secrets`** — `pnpm --dir apps/dashboard install`과 `pnpm --dir apps/dashboard build`를 돌린 뒤 `bash scripts/ci_check_bundle_secrets.sh`를 실행한다. 빌드가 실패하면 그 스텝에서 잡이 실패하고, 빌드는 성공했는데 산출물이 없으면 스크립트가 실패시킨다
4. **`pytest`** — `uv sync` 후 `uv run pytest`를 저장소 루트에서 돌린다. `testpaths`에 `apps/worker/tests`가 들어 있어야 worker 테스트가 함께 돈다 (02-02-PLAN이 추가했다). ⚠️ DB가 필요한 통합 테스트(02-04-PLAN의 격리 테스트, 02-07-PLAN Task 3의 큐 통합 테스트)는 로컬 Supabase 스택을 요구한다. CI에서 Supabase 스택을 띄울지, 아니면 그 테스트들을 마커로 분리해 CI에서는 단위 테스트만 돌릴지 선택하고 **그 선택과 근거를 워크플로우 주석과 `docs/ops/ci-security-gate.md`에 명시한다**. 어느 쪽이든 "DB가 없어서 조용히 건너뛴다"는 결과가 되면 안 된다 — 건너뛴 것은 건너뛴 것으로 보여야 한다

⚠️ 어떤 보안 게이트 스텝에도 실패를 삼키는 구문을 쓰지 않는다. SPEC Prohibitions 4행이 금지한 네 가지 구문 — 잡/스텝 수준의 에러 무시 플래그, 항상 참을 반환하는 파이프 꼬리, 셸의 오류 중단 해제, 빈 결과를 통과로 처리하는 것 — 이 워크플로우에는 하나도 들어가지 않는다. SEC-03의 요구는 워크플로우의 존재가 아니라 **빌드 실패**다. 이 사실을 워크플로우 상단 주석에 적는다.

각 잡에 의존성 캐시를 붙여도 좋지만, 캐시 복원 실패가 잡을 통과시키는 형태가 되지 않게 한다.

워크플로우가 secret을 요구하지 않도록 설계한다 — 네 검사 중 어느 것도 Supabase나 OpenRouter 자격증명이 필요 없다. 필요해 보이면 그 검사가 잘못 설계된 것이다.
