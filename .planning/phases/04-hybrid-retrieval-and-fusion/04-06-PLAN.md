  <action>Within the existing transaction, seed a dedicated fixed-UUID workspace/source/wiki corpus large and selective enough for the local pgvector planner to choose each deployed HNSW index without disabling sequential scans or globally forcing planner methods. Because `EXPLAIN SELECT * FROM public.search_chunks(...)`/`search_wiki_embeddings(...)` can stop at a Function Scan and cannot prove a function-internal HNSW scan when the RPC owns function-level SET GUCs, build security-equivalent direct source/wiki SELECTs for plan observation: same authenticated/RLS context, `workspace_id` and non-null predicates, `extensions.<=>` order expression, and `least(greatest(p_k, 1), 100)` limit. In each EXPLAIN transaction issue `SET LOCAL hnsw.iterative_scan = 'strict_order'`, `SET LOCAL hnsw.ef_search = '200'`, and `SET LOCAL hnsw.max_scan_tuples = '40000'` before the direct query. Keep fixture inserts and SET LOCAL effects isolated to the test transaction and do not modify migrations, index definitions, or production policy to make the test pass.</action>

    - The fixture has documented cardinality/selectivity rationale and uses valid 1024-dimensional vectors for both source and wiki embeddings.
    - The test neither uses `enable_seqscan = off` nor another forced planner setting, and it rolls back all fixture rows and role/session changes.
    - Both plan-observation queries run as the authenticated fixture requester with a predicate/order/limit and HNSW GUC values proven equivalent to the deployed RPC contract; the test does not EXPLAIN an RPC and infer its internal plan.
  </acceptance_criteria>
