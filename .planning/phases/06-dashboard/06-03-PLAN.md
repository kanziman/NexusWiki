<objective>
Deliver a fully working member roster + email-based invite for UI-02/D-04, closing a real
backend gap this plan discovered: no capability anywhere (Supabase Auth, `apps/api`, or the
schema) can resolve an email to a `workspace_members.user_id`, or return a member's email for
display, because `auth` is not one of `supabase/config.toml`'s exposed PostgREST schemas
(`schemas = ["public", "graphql_public"]`) and `workspace_members` only stores `user_id uuid`.
`apps/api`'s `workspaces.py` (the only workspace router Phase 5 shipped) has PATCH/DELETE on
`workspaces` itself and nothing member-related; grep across the whole repo confirms no
invite/member router or RPC exists anywhere pre-Phase-6.

`06-CONTEXT.md`'s Phase Boundary states this phase "does not add backend capabilities" and the
schema-push-detection gate explicitly told this planner to "stop and reconsider" before adding
a migration file. Having stopped and reconsidered: the alternative to adding one is either (a)
shipping a fake invite form that always fails (silently reducing D-04's locked scope — forbidden
by this planner's own operating rules), or (b) routing invite through a new user-facing
service-role code path (forbidden outright — `service_role`/`WorkerSettings` is worker+migration
only, per `checklists.json > decisions.db_access` and SEC-01/SEC-05). Neither is acceptable, so
this plan adds the smallest possible closure: two `SECURITY DEFINER` SQL functions using the
EXACT idiom `0001_core_schema.sql`'s `add_owner_as_member()` already established (a definer
function reading/writing across a privilege boundary a plain RLS policy cannot cross) — no new
table, no RLS policy change, no `apps/api` change, no `service_role` anywhere.

Purpose: make D-04's invite form real, not decorative.
Output: migration `0014`, `MembersList.tsx`, `InviteForm.tsx`, the settings page.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> invite_workspace_member RPC | A workspace owner's session crosses into a SECURITY DEFINER function that reads `auth.users` (a schema the caller's own JWT could never query directly) |
| Browser -> workspace_members DELETE | Direct table write, RLS-enforced (no definer function involved) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-08 | Elevation of Privilege | invite_workspace_member | high | mitigate | `has_workspace_role(p_workspace_id, 'owner')` checked as the FIRST statement in the function body, raising 42501 before any auth.users read — an editor/viewer cannot invite anyone regardless of what role they request |
| T-06-09 | Elevation of Privilege | invite_workspace_member p_role | high | mitigate | `p_role not in ('owner','editor','viewer')` is rejected server-side (22023); the client-side Select only offers the three valid values but the function does not trust that |
| T-06-10 | Information Disclosure | invite_workspace_member NW404 | medium | accept | Owner-only email-registration-status enumeration; judged and accepted (see must_haves.prohibitions), standard practice for invite-by-email products |
| T-06-11 | Information Disclosure | workspace_members_list | medium | mitigate | `is_workspace_member(p_workspace_id)` gates the whole function — a non-member caller gets 0 rows, never another workspace's roster |
| T-06-12 | Tampering | workspace_members DELETE | high | mitigate | Enforced entirely by the pre-existing `workspace_members_delete_owner` RLS policy (0004) — this plan adds no new write surface for removal |
</threat_model>
