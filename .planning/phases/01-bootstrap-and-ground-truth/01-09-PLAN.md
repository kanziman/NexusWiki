    구현 파일을 먼저 바꾸지 말고 테스트 두 건을 추가한다.

    첫 테스트의 함수 이름은 정확히 `test_redacts_sensitive_values_inside_one_level_sequences`로 하고,
    one-level sequence 경로를 고정한다. event에 list와 tuple을 각각 포함시키고 그 원소인
    mapping에 `authorization: "Bearer sequence-secret"`와 `email: "sequence@example.com"`을 둔다.

    둘째 테스트의 함수 이름은 정확히 `test_redacts_sensitive_values_across_nested_sequences`로 하고,
    mapping → list → tuple → mapping처럼 sequence와 mapping이 여러 단계 교차하는 경로에
    `token` 또는 `content` sentinel을 넣는다. 가장 깊은 값이 마스킹되고, 안전한 이웃 값과 각 list/tuple
    container type이 그대로인지 단언한다. 테스트 assertion 실패 메시지나 fixture 출력에도 실제 credential,
    이메일, 사용자 content를 쓰지 말고 명백한 synthetic sentinel만 사용한다.

    RED 단계로 위 두 node ID만 정확히 선택해 실행하고, 현재 구현에서 assertion failure를 뜻하는 pytest exit
    status 1만 허용한다. 출력은 저장소 밖 `mktemp` 파일에 저장하고 화면에 출력하지 않는다. status 2(사용법/수집),
    3(internal error), 4(usage error), 5(no tests collected), 또는 그 밖의 status는 RED로 인정하지 않는다. 또한
    저장된 출력에 collection/import/no-tests/internal error 표지가 있으면 status 1이어도 거부하고 테스트 자체를
    먼저 고친다. 임시 출력은 trap으로 삭제하며 실제 synthetic sentinel이나 assertion diff를 출력하지 않는다.
    Task 1에서는 production implementation을 수정하지 않는다.

    `_redact_mapping`의 mapping-only 분기를 recursive value walker로 일반화한다. walker는 값을 받아 다음 규칙을
    정확히 적용한다: mapping이면 각 key를 `casefold()`해 denylist 일치 값은 즉시
    `REDACTION_PLACEHOLDER`로 바꾸고, 안전한 key의 값은 다시 walker에 넘긴다; list이면 각 원소에 walker를
    적용한 list를 반환한다; tuple이면 각 원소에 walker를 적용한 tuple을 반환한다; 그 밖의 scalar는 그대로
    반환한다. 문자열/bytes를 일반 Sequence로 취급하지 말고, 이번 blocker에 필요한 list와 tuple만 명시적으로
    지원한다. list는 list, tuple은 tuple이라는 container semantics를 보존한다.

    기존 `redact_sensitive(logger, method_name, event_dict)` processor signature와 반환 mapping 계약,
    `REDACTED_KEYS`, `REDACTION_PLACEHOLDER`, processor 순서, context binding API는 변경하지 않는다. 새 패키지,
    새 env key, 새 로그 필드, broad serializer normalization은 추가하지 않는다. in-place mapping 동작을 유지해
    structlog processor chain과의 wiring을 바꾸지 않는다.

    GREEN 단계에서 focused logging tests를 통과시킨 뒤, 기본 Python suite와 ruff를 실행한다. 마지막으로
    `bash scripts/smoke_tracer.sh`를 실행해 API와 worker가 수정된 core logging processor를 사용한 상태에서도
    health와 lifecycle tracer가 통과하는지 확인한다. 테스트 실패 시 민감 sentinel 또는 event payload 전체를
    디버그 로그로 출력하지 않는다.
  </action>

## Security Gate

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 호출자 payload → `redact_sensitive()` | 외부 요청/잡 metadata가 mapping과 sequence가 섞인 임의 형태로 공용 로깅 processor에 들어온다 |
| `redact_sensitive()` → renderer/stdout | redactor가 놓친 값은 production JSON renderer를 거쳐 Railway 등 로그 저장소에 평문으로 영구 노출될 수 있다 |
