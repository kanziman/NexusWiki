NexusWiki — DB 접근 구조

누가 어떤 자격으로 DB에 접근하고, 질문 하나가 어떤 경로로 답변이 되는가.
기준: 마이그레이션 0001~0006 (2026-08-01)
구현 완료 — DB 레이어 설계 확정 — 앱 레이어(Phase 2) 미구현

이 프로젝트의 핵심은 "원문 + 위키 이중 출처"입니다. 답변 한 줄마다 컴파일된 위키 근거와 원본 문서의 해당 위치를 함께 제시합니다. 그걸 가능하게 하려고 DB가 5개 검색 채널을 갖고 있고, 팀 단위 격리를 코드가 아니라 DB가 강제합니다.

01세 개의 역할 — 누가 어떤 자격으로 붙는가

DB에 접근하는 주체는 셋뿐입니다. 이 구분이 보안의 전부라서 가장 먼저 봐야 합니다.

앱 코드에서 가장 중요한 한 가지. Supabase 클라이언트를 user_client(jwt) / service_client() 두 개로 분리하고, 사용자 요청 경로에서는 절대 후자를 쓰지 마세요. 한 번이라도 섞이면 이 격리 전체가 무의미해집니다. (P0-INIT-02)

왜 5개인가

원래 계획에는 Neo4j로 그래프 채널을 만들 예정이었지만, Aura 기본 티어에 GDS가 없고 이 규모에선 순회 성능 이점도 없으며 팀 모드에서는 Neo4j에 RLS가 없어 보안 부담만 늘어서 제외했습니다. 대신 wiki_links 테이블 + recursive CTE로 5번 채널을 Postgres 안에서 해결합니다.

채널대상방식인덱스답변에서의 역할
1wiki_embeddings벡터 유사도HNSW정리된 설명을 의미로 찾음
2source_chunks벡터 유사도HNSW원문 인용의 출처
3wiki_pagesbigram 어휘GIN사내 약어·제품명 정확 매칭
4source_chunksbigram 어휘GIN원문의 정확한 표현 매칭
5wiki_linksN-hop 순회B-tree연관 문서까지 끌어옴

한국어 검색이 bigram인 이유

Postgres 기본 FTS에는 한국어 형태소 분석기가 없어서 공백 단위로만 쪼갭니다. pg_bigm/pgroonga는 호스팅 Supabase가 제공하지 않습니다. 그래서 애플리케이션이 문자열을 2글자씩 잘라 to_tsvector('simple', ...)에 넣습니다. 의존성이 0이고 사내 약어·신조어를 놓치지 않습니다.

절대 하면 안 되는 것. search_tsv를 generated column으로 만들면 DB가 직접 to_tsvector를 돌려 한국어가 공백 단위로만 쪼개지고 검색이 사실상 무용해집니다. 반드시 앱이 채우는 일반 컬럼이어야 합니다. 또 색인할 때와 질의할 때 같은 토크나이저를 써야 합니다 — 어긋나면 에러 없이 조용히 안 맞습니다. (그래서 tsv_tokenizer_version 컬럼을 뒀습니다)
질의 측 함정 — 실제로 밟았습니다. bigram 문자열을 to_tsquery에 그대로 넣으면 "한국 국어"처럼 공백으로 이어져 syntax error가 납니다. phraseto_tsquery('simple', bigram(q))를 쓰세요. bigram들이 <->로 묶여 인접성까지 검사하므로 부분 문자열 의미가 보존됩니다. plainto_tsquery는 &로 묶여 순서 뒤바뀐 오탐이 섞입니다.

이중 Citation이 성립하는 조건

컨텍스트를 조립하는 쪽이 각 청크 앞에 인용 앵커를 붙여야 합니다. 위키 청크는 wiki:slug, 원문 청크는 src:청크id 형태입니다. 앵커가 없으면 모델이 인용 표기를 만들어낼 근거 자체가 없어서 이중 Citation이 에러 없이 조용히 무너집니다. 0006의 프롬프트 4종이 이 표기를 강제하고 있습니다.

SECURITY DEFINER가 없으면 무한 재귀로 죽습니다. workspace_members의 정책이 "내가 이 워크스페이스 멤버인가"를 확인하려고 workspace_members를 다시 조회하면 42P17 infinite recursion detected in policy가 납니다. SECURITY DEFINER 함수로 감싸서 그 고리를 끊습니다. STABLE을 빠뜨리면 행마다 재평가되어 성능이 무너지고, SET search_path를 빠뜨리면 호출자가 가짜 테이블을 심을 수 있어 권한 상승이 됩니다.

위반이 항상 에러는 아닙니다 — API가 반드시 알아야 할 것

즉 권한 없는 UPDATE/DELETE는 "성공했는데 아무것도 안 바뀜"으로 돌아옵니다. API는 영향 행 0 = 403으로 매핑해야 합니다. 남의 워크스페이스로 쓰려는 시도(WITH CHECK 위반)만 42501 예외로 옵니다.

RLS가 벡터 검색의 사후 필터로 동작합니다. 실제 실행 계획에서 확인했습니다: Index Scan using source_chunks_embedding_idx → Filter: is_workspace_member(workspace_id) → Rows Removed by Filter: 5. HNSW가 뽑은 후보가 여기서 걸러지므로 결과가 요청한 k개보다 적게 나올 수 있습니다. 검색 쿼리는 ① where workspace_id = $1을 명시하고 ② set local hnsw.iterative_scan = strict_order를 켜야 합니다.

읽기와 달리 쓰기는 역할이 중간에 바뀝니다. 사용자 JWT로 시작해서, 잡을 거쳐, service_role 워커로 넘어갑니다.

failed는 종착점이 아니라 "직전 시도 실패, 백오프 후 재시도 예정"입니다. 사람이 손대야 하는 종착점은 dead 하나뿐입니다. 둘을 나눠 두면 프론트가 "3번 중 2번째 실패, 4분 후 재시도"를 그대로 보여줄 수 있습니다.

잡은 at-least-once입니다. 워커가 죽으면 락 타임아웃(기본 15분) 후 회수되어 다시 실행됩니다. 타임아웃이 정상 잡의 최장 실행 시간보다 짧으면 살아 있는 워커의 잡을 뺏어 이중 처리됩니다. 그래서 모든 핸들러가 멱등해야 하고, 그걸 받쳐주는 게 스키마의 유니크 키 3개입니다 — (workspace_id, slug) · (raw_source_id, chunk_index) · (wiki_id, chunk_index).

두 개의 레이어

  • Layer 1 · 원문 — raw_sources + source_chunks. 불변입니다. 사용자 UPDATE 정책이 아예 없습니다. char_start/char_end로 원문의 정확한 위치를 가리켜 인용이 "어디에 그렇게 쓰여 있는지"를 증명합니다.
  • Layer 2 · 위키 — wiki_pages + wiki_embeddings + wiki_links. LLM 컴파일 산출물입니다. 언제든 다시 만들 수 있습니다.

wiki_links.to_wiki_id가 NULL이면 red link(아직 없는 문서를 가리키는 링크)입니다. 그 자체가 "다음에 만들 위키" 목록이 됩니다. 나중에 같은 slug의 위키가 생기면 자동으로 이어지고, 대상이 삭제되면 다시 red link로 돌아갑니다.

왜 벗어났는가

  • workspaces UPDATE = owner — 이 UPDATE가 곧 owner_id 이전, 즉 소유권 양도입니다. editor에게 열면 editor가 스스로를 소유자로 만듭니다.
  • workspace_members 쓰기 = owner — editor에게 INSERT를 열면 자신을 owner 역할 행으로 추가해 즉시 권한이 상승합니다.
  • 파생 3종 읽기 전용 — 전부 워커가 만드는 데이터입니다. 특히 source_chunks에 INSERT를 열면 editor가 원문에 없는 청크를 심어 이중 Citation의 원문 측 인용을 위조할 수 있습니다. 제품의 신뢰 근거를 사용자 입력에 노출시킬 이유가 없습니다. 워커는 service_role이라 아무 영향도 받지 않습니다.
  • jobs 읽기 전용 — 생성과 상태 전이는 전부 서버 경로입니다. 큐 조작 함수 4종도 anon/authenticated의 실행 권한을 회수해 뒀습니다. (Supabase는 public 스키마 함수에 기본 실행 권한을 주므로, 놔두면 PostgREST의 /rpc/로 남의 잡을 점유·종료할 수 있습니다)

소유자를 잠그는 두 개의 트리거

workspaces INSERT  →  소유자를 멤버로 자동 등록      (0001)
workspace_members UPDATE/DELETE  →  소유자 행 보호   (0004)

멤버가 0명인 워크스페이스는 RLS 아래에서 아무에게도 보이지 않아 영구 복구 불가가 됩니다. 0001이 생성 시점을 막고, 0004가 그 이후를 막습니다 — 소유자는 자기 멤버십을 삭제하거나 역할을 낮추거나 user_id를 바꿀 수 없습니다. 소유권 이전은 workspaces.owner_id를 바꾸는 경로로만 가능합니다.
