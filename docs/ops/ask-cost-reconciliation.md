# Ask 미확정 비용 운영

관련 이슈: #172, #177~#181. 설계 결정은 `openspec/changes/reconcile-interrupted-ask-cost/design.md`를 따른다.

## 정책 설정

워커의 `ASK_COST_POLICIES`는 `LLM_MODEL`과 정확히 일치하는 키를 가진 JSON 객체다. 각 항목은 `reserve_micros`, `max_input_bytes`, `max_tokens`, `version`을 요구한다. 미설정·잘못된 정책·모델 불일치는 Ask 공급자 호출 전에 503으로 거부한다. 임베딩과 수집 워커 기동 자체를 막지는 않는다.

숫자 기본값은 제공하지 않는다. 운영자는 사용할 모델의 입력·출력 가격과 캐시·추론 토큰 등 청구 조건을 확인하고, 전체 messages 입력 바이트 한도 및 최대 출력에 대한 보수적 추정액에 여유분을 더해 확보액을 정한다. 가격 확인 날짜·공식 가격 출처·모델·입력 및 출력 한도·여유분 근거를 배포 승인 기록에 함께 남긴다. 모델이나 한도를 바꾸면 정책 버전과 확보액을 함께 검토한다. 코드의 단위 검증에서 쓰는 `m/v1/100`은 합성 수치이며 운영 가격 근거가 아니다.

확보액은 실제 청구 상한이 아니다. 가격·토크나이저 차이 등으로 실제 비용이 확보액을 넘을 수 있고, 조회 불가 호출의 실제 금액에는 검증된 절대 상한이 없다. 공급자 실제 비용을 확인하면 초과액도 전액 반영한다. 전체 워크스페이스의 엄격한 상한은 보장하지 않는다. 수집·임베딩·컴파일은 사전 금액 예약 범위에 포함되지 않는다.

## 금액 해석

- 공급자 보고 비용: 유효한 최종 사용량 또는 사후 대조로 확인한 금액. 미해결 호출은 이미 보고된 관측액만 여기에 포함된다.
- 미확정 예산 점유: 확보액 중 이미 보고된 비용을 제외한 추가 점유액이다. 실제 청구액이 아니다.
- 예산 판정액: 두 금액의 합이며 신규 Ask 예약과 수집 인큐에 사용한다. 확정 정산이 끝나면 확보액 대신 확정액만 남는다.

기존 `usage_events`는 원 관측 이력으로 보존된다. 신규 호출의 유효 비용은 정산 투영으로 조회하므로 원시 사용량 합계와 다를 수 있다. 동일 call_id는 공급자 재호출 키가 아니며, 스트림 공급자 호출은 자동 재전송하지 않는다.

## 미해결 호출

generation 메타데이터만 조회한다. 워커는 최대 5건을 순차 대조하고, 조회는 건당 5초 제한이며 10초 주기로 작업을 확인한다. 조회와 DB 왕복 시간을 포함하도록 DB 임대는 180초다. 첫 자동 대조는 예약 후 5분 이후, 실패 후 지연은 30초부터 지수 증가하며 최대 1시간이다. 8번 실패하거나 ID가 없으면 `manual_review`로 표시하고 자동 재시도를 멈춘다. ID 충돌도 자동 정산을 막는다. 공급자 응답 원문·ID·본문·키는 로그와 화면에 표시하지 않는다.

임대 만료는 재시도를 허용할 뿐 예산 점유를 해제하지 않는다. 전송 직전 종료 등으로 실제 전송 여부를 모르면 예약을 유지한다. 전송을 시작하지 않았음이 현재 실행에서 확인되는 취소만 해제한다. 오래됐다는 이유로 미해결 비용을 0으로 정산하지 않는다. 수동 금액 조정 UI는 제공하지 않으므로 운영자는 비용 근거를 확보한 뒤 별도 승인된 복구 절차를 마련한다.

호출은 시작한 UTC 월에 귀속된다. 다음 달에 정산해도 새달에 다시 부과하지 않으며, 과거달의 미해결 점유를 새달로 이월하지 않는다.

## 적용과 롤백

`0027`은 새 테이블·RPC·공통 예산 집계를 추가한다. 원격 최신 `0026`은 구현 시작 시 `supabase migration list --linked`로 읽기 확인했다. 운영에는 적용하지 않았다. 로컬 DDL과 계약 검증은 `supabase/tests/ask_cost_accounting.sql`로 수행한다. 운영 적용 직전에는 원격 원장과 dry-run 대상을 다시 확인한다.

로컬 검증 기록(2026-11-02): `docker exec ... psql -v ON_ERROR_STOP=1`로 DDL을 적용하고 개발 중 함수 변경분을 로컬에 갱신했다. SQL 계약·실제 PostgREST 병렬 승인·정산·작성자 권한 테스트를 통과한 뒤 `supabase migration repair 0027 --status applied --local`로 직접 적용한 로컬 원장을 맞췄고, `migration list --local`에서 `0027` 일치를 확인했다. 이 조치는 클라우드 원장 변경이나 원격 불일치 우회가 아니다.

1. 운영자가 신규 Ask 유입을 중지하고 기존 스트림 종료를 기다린다. 그 구간의 구 워커 중단 호출은 새 회계로 소급 복구할 수 없다.
2. `supabase migration list --linked` 및 `supabase db push --linked --dry-run`으로 대상·호환성을 확인하고 승인된 운영자가 DB를 선적용한다. 적용 성공과 미적용 대상 0건을 명령으로 확인한다.
3. 모델 정책과 입력·출력 한도를 검토해 새 워커·API·대시보드를 모두 전환한다. 구 워커가 남아 예약 없이 호출하지 않게 확인한다.
4. 운영자가 실제 소액 Ask의 예약·정산, Control Room 금액 구분, 중단 후 대조를 확인하고 유입을 재개한다. 테스트 fixture 통과를 실제 청구 확인으로 간주하지 않는다.

활성 예약이 생긴 뒤에는 구 코드로 단순 롤백하지 않는다. 신규 Ask를 중지한 상태에서 예약을 인식하는 버전으로 복구하거나 운영자에게 이관한다. 테이블 삭제·기존 usage 수정·원장 repair로 비용 기록을 지우지 않는다. 운영 중지·DB push·실제 유료 호출·머지는 별도 승인이 필요하다.
