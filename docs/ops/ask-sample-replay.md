# Ask 합성 샘플 재생 기록

`scripts/ask_replay.py`는 가상의 물류 회사 문서 8건과 고정 질문 30개를 실제 LLM으로 재생해 코드 전후를 비교한다. 2주 기준선 대신 쓰기로 2026-11-03에 결정했다. 근거: `openspec/changes/ai-control-output-contract/design.md`.

⚠️ 합성 샘플 수치다. 운영 트래픽의 효과로 인용하면 안 된다. 질문 수가 적고 LLM 답변이 매번 달라 작은 차이는 의미가 없다.

## 실행

```bash
# 544xx와 분리된 546xx 스택을 띄운다. 공유 스택의 큐에 붙으면 다른 테스트의 잡을 가져간다.
scripts/ask_replay_stack.sh start /tmp/ask-replay
# 비교할 코드로 API와 워커를 띄운다. 워커 내부 포트 8081은 고정이라 한 번에 한 벌만 띄운다.
scripts/ask_replay_serve.sh <코드 루트> /tmp/ask-replay/logs &
uv run python scripts/ask_replay.py seed --state state.json
uv run python scripts/ask_replay.py ask --state state.json --label after --out after.json
uv run python scripts/ask_replay.py compare before.json after.json
```

## 성적표 (질문별 통과 판정과 화면)

`ask`를 돌릴 때마다 `--out` 옆 `scorecard.jsonl`에 한 줄이 쌓인다(`--scorecard`로 위치 지정). 줄에는 label · git sha · 모델 · 통과율 · 입력/출력 토큰 · 비용 · 지연 p50/p95 · 결과 파일 상대 경로만 있고, 질문과 답변 본문은 없다. 파일은 저장소 밖에 두며 합성 수치라 커밋하지 않는다.

```bash
# 눈으로 보기. 네트워크도 스택도 필요 없고 비용이 들지 않는다.
uv run python scripts/ask_replay.py report --scorecard /tmp/ask-replay/scorecard.jsonl --html /tmp/ask-replay/scorecard.html
# 성적표 줄이 생기기 전의 옛 결과 파일도 더할 수 있다.
uv run python scripts/ask_replay.py report --scorecard ... --html ... --result before.json
```

생성된 HTML은 파일 하나다(외부 의존 없음). 일부 브라우저는 `file://`을 막으므로 열리지 않으면 폴더에서 `python3 -m http.server`로 연다. 위쪽 표에서 실행을 누르면 아래에 30문항 상세와 실패 이유가 나온다.

통과 조건(정답이 있는 질문): 상태가 `resolved` · 위조 앵커 0건 · 기대 사실 판정이 거짓이 아님 · 답변이 위키와 원문을 각각 한 번 이상 인용(`cited_wiki_count ≥ 1`, `cited_source_count ≥ 1`, 서로 다른 문장이어도 된다). 이 두 필드가 없는 옛 결과 파일은 `dual_citation_rate > 0`(한 문장에 둘 다 있는 문장 비율)으로 대체하며, 이 경우가 더 엄격해 이유에 "옛 결과, 문장 기준"이 붙는다. 이유는 이 순서의 첫 실패 하나만 적는다. `fallback`은 인용 계약 수리에 실패한 답이라 불통과다. 답할 수 없는 질문(`doc: none`)은 위조 앵커가 0건이면서 둘 중 하나일 때 통과다. (a) 상태가 `no-evidence`(검색이 근거를 못 찾음), 또는 (b) 상태가 `resolved`이고 답변의 첫 본문 줄(`#` 제목 줄과 빈 줄 제외)이 표준 거절 문구 "제공된 자료로는 알 수 없습니다"로 시작(공백 차이 무시). 무관한 근거가 검색돼 모델까지 간 뒤 정확히 거절한 경우가 (b)다. 문구는 답변 프롬프트(`0006_seed_prompts.sql`)가 지시하는 것이며 프롬프트가 바뀌면 `REFUSAL_STATEMENT`도 바꿔야 한다. 알려진 한계 둘: 질의 임베딩 일시 실패 같은 장애의 `no-evidence`도 통과로 세고, 거절 문구로 시작한 뒤 이어서 답하는 혼합 답변도 통과할 수 있다(위조 앵커만 잡는다). 판정은 저장된 값이 아니라 행 필드에서 화면을 만들 때마다 다시 계산하므로, 기준을 바꿔도 옛 결과를 재채점할 수 있다.

첫 실제 재생(2026-11-07, `claude-sonnet-4.6`, 코드 `c97d3b3` + 성적표 변경): 27/30 통과(90%) · 입력 토큰 195,113 · 문항당 $0.0274 · p50 9.8초 · p95 21.9초 · 위조 앵커 0건. 문서 수집 약 $0.22, 질문 30개 약 $0.82. 실패 3건은 q06(기대값 `2시간`인데 모호한 질문에 반품 검수 48시간으로 답함, 질문 세트 문제일 수 있음), q26(정답 키워드는 있으나 한 문장에 위키·원문을 함께 인용한 문장이 없음. 이 재생은 종류별 개수를 기록하기 전이라 문장 기준으로 판정됐고, 답변 단위로는 통과였을 수 있다), q30(존재하지 않는 회사의 영업이익을 묻는 질문. 답변은 "제공된 자료로는 알 수 없습니다"로 정확히 거절했지만 상태가 `resolved`라 당시 규칙이 실패로 셌다. 환각이 아니라 판정 규칙의 한계였고, #224에서 거절 문구를 통과로 인정하도록 고쳤다. 이 재생을 지금 규칙으로 다시 채점하면 q30은 통과다)이다. 한 번의 결과이고 답변이 매번 달라 실패 문항은 재실행 때 바뀔 수 있다.

지연은 클라이언트가 잰 시간(큐 대기·네트워크 포함)이다. p50/p95는 입력 토큰 p95와 같은 인덱스 방식(`int(비율 × n)`)이라 30문항에서 p95는 사실상 29번째 값, 즉 최댓값 근처다.

## 검색만 채점 (`retrieval-eval`)

답변을 만들지 않고 검색 API만 돌려 질문마다 정답 문서를 찾았는지 센다. 답변 LLM 호출이 없고 비용은 질의 임베딩뿐이다. 기록은 새 파일로만 쓰며 이미 있는 경로는 덮어쓰지 않는다.

```bash
uv run python scripts/ask_replay.py retrieval-eval --state state.json --label <이름> --out <기록.json>
uv run python scripts/ask_replay.py retrieval-compare before.json after.json
```

정답 판정: 원문 근거는 그 근거의 raw_source가 정답 문서면 적중, 위키 근거는 그 페이지를 만든 원문(`wiki_pages.sources`)에 정답 문서가 있으면 적중이다. ⚠️ 원문 근거의 `document_id`는 raw_source id가 아니라 청크 id다. raw_source는 `metadata.raw_source_id`로 찾고, 없으면 청크 id로 조회한다.

지표 정의: hit@k는 정답 근거가 하나라도 상위 k에 있는 질문의 비율(hit rate)이고, MRR은 첫 적중 순위의 역수 평균이며, 이중 적중@8은 상위 8 안에 정답 원문과 정답 위키가 둘 다 있는 질문의 비율이다. 답할 수 있는 질문만 센다.

측정(2026-11-08, 코드 `3c62233` + 이 변경, 정책 `hybrid-rrf-v1`, 답할 수 있는 29문항, 위키 13쪽, 채널 장애 0건):

| 지표 | 값 | 95% 구간 | 무작위 기대 |
| --- | --- | --- | --- |
| hit@1 | 16/29 | 37.5~71.6% | 0.143 |
| hit@3 | 23/29 | 61.6~90.2% | — |
| hit@8 | 29/29 | 88.3~100% | — |
| MRR | 0.696 | — | — |
| 위키만 hit@8 | 29/29 | — | **0.589** |
| 원문만 hit@8 | 27/29 | 78.0~98.1% | — |
| 이중 적중@8 | 27/29 | 78.0~98.1% | — |

여러 문서 질문 3개 중 하나라도 찾음 3, 전부 찾음 3. 측정 실패 0. 답할 수 없는 q30에는 근거 8건이 돌아왔다.

같은 날 앞서 한 측정(문서를 따로 수집해 위키 11쪽)은 hit@1 19/29, 여러 문서 전부 찾음 2/3이었다. 그 기록은 채널 상태를 남기기 전이라 장애 여부를 가릴 수 없어 기준으로 쓰지 않는다. 두 측정의 차이는 코드가 아니라 **재수집마다 위키가 다르게 컴파일된 것**(11쪽 → 13쪽, 배송 문서 페이지 1 → 5)에서 나왔다. 검색 지표를 비교할 때는 같은 수집 결과 위에서 재야 한다.

해석:

- **모든 질문에서 상위 6개가 위키이고 원문은 7~8위에 1~2개만 온다.** 채널 장애는 0건이라 장애가 아니라 정상 동작이다. 그래서 순위 지표(hit@1, MRR)는 사실상 "정답 위키가 위키 중 몇 번째인가"를 잰다.
- **위키만 hit@8은 부풀려진 지표다.** 위키가 13쪽뿐인 워크스페이스에서 질문과 무관하게 6쪽을 돌려줘도 정답 위키가 들어갈 기대값이 0.589다. 29/29를 검색 품질로 읽으면 안 된다. 의미 있는 신호는 hit@1(16/29, 무작위 기대 0.143)이다.
- **원문은 1~2칸만 받는데도 27/29를 찾았다.** 놓친 두 문항은 q06(창고 질문에 반품 문서가 잡힘)과 q20이다. q06은 첫 성적표에서 답변이 "반품 검수 48시간"으로 틀린 문항이라, 그 실패의 처음 틀어진 단계가 검색일 가능성이 크다.
- q26은 첫 성적표에서 이중 인용 실패였지만 검색은 정답 원문과 위키를 모두 찾았다. 실패의 원인은 검색이 아니라 작성 또는 당시의 문장 기준 판정이다.
- 위키가 상위를 차지하는 이유는 측정으로 확인하지 않았다. 코드상 RRF가 위키는 페이지 단위로 묶으면서 같은 채널의 청크 점수를 더하고, 원문은 청크마다 따로 경쟁한다(`nexuswiki_core/rrf.py`). #195가 이 동작을 다룬다. 이 순서는 검색 API의 순서이고 Ask 컨텍스트는 이중 근거 쿼터로 따로 조립된다.

## RRF 같은 채널 중복 제거 실험 (2026-11-08)

변경 계약은 `openspec/changes/archive/2026-11-08-retrieval-rrf-channel-dedupe/design.md`다. 같은 수집 결과를 유지한 546xx 스택에서 `hybrid-rrf-v1`(합산)과 `hybrid-rrf-v2`(최고 순위 한 번)를 비교했다. 답할 수 있는 29문항 기준이며 검색 측정 실패는 양쪽 모두 0건이다.

| 지표 | v1 합산 | v2 최고 순위 |
| --- | --- | --- |
| hit@1 | 18/29 | 27/29 |
| MRR | 0.713 | 0.940 |
| hit@8 | 29/29 | 28/29 |
| 이중 적중@8 | 27/29 | 28/29 |
| 상위 6 안에 원문 근거가 있는 질문 | 0/29 | 29/29 |

before 기록의 위키 근거 188건 중 180건은 `wiki_vector` 기여가 단일 최고 순위의 최대치 `1/61`을 넘었다. 같은 채널의 여러 청크가 페이지 하나에 합산된다는 원인 가설을 기록으로 확인했다. 이 수치는 모든 질문에서 위키가 정확히 6건이었다는 뜻은 아니다.

검색 회귀는 q06과 q20이다. q06은 정답 위키가 4위에서 상위 8 밖으로 밀려 hit@8이 실패했다. 원문 검색이 반품 문서로 빗나가던 기존 약점과 연관됐을 가능성이 있으나, 이번 변경에서 관측한 회귀로 남긴다. q20은 첫 적중이 2위에서 4위로 내려갔고 원문·위키 적중은 유지했다. 나머지 27문항은 첫 적중 순위가 같거나 좋아졌다.

공식 벤치마크의 유효한 기록은 [before](benchmark-records/fusion-195b-v1-sum-strict.json)와 [after](benchmark-records/fusion-195b-v2-best-rank-strict.json)다. `compare-fusion-records`는 같은 핀과 융합 방식·버전만의 차이를 확인해 `ok`를 반환했다. 통과율과 recall은 26/36 → 27/36, MRR은 0.316 → 0.563, 전체 언더필은 0 → 0이다. 앞선 `fusion-195-*` 기록은 벤치마크 임베딩 클라이언트의 인자 불일치로 벡터 채널이 실패한 무효 기록이다. 덮어쓰지 않고 보존하며 채택 근거로 쓰지 않는다. 로컬 Docker 지연은 운영 지연 근거로 쓰지 않는다.

첫 after와 추가 재시도는 각각 30문항 모두 `error`였다. 무효 실행으로 보존하며 아래의 정상 재생과 구분한다.

추가 재시도의 실패 원인은 첫 실행과 구분한다. 내부 `/internal/llm-chat` 응답은 예산 초과 402가 23건, 요청 제한 429가 7건이었다. 재생 DB 확인 결과 월 한도는 $5, 유효 사용·예약 합계는 $4.851316이며, 호출당 예약 $0.20을 더하면 한도를 넘는다. `unresolved` 19건의 예약액 $3.80이 포함돼 있다. 따라서 공급자 크레딧 충전만으로 재시도가 성공한다고 볼 수 없다. 내부 예산·미정산 상태를 확인하고 한 문항 성공을 확인한 뒤 전체를 재생해야 한다. 미정산 기록은 임의로 삭제하거나 사용액 0으로 처리하지 않는다.

사용자 승인 후 같은 수집 위에서 한 문항을 먼저 정상 완료한 뒤 after 30문항을 새로 재생했다. 결과는 30문항 모두 `resolved`, 29/30 통과이며 q30은 정확한 거절로 통과했다. before q30은 공급자 크레딧 소진으로 무효이므로 전후 비교에서는 양쪽 q30을 제외한다.

| 답변 지표 (공통 29문항) | before | after |
| --- | --- | --- |
| 성적표 통과 | 23/29 | 28/29 |
| 위조 앵커 | 0건 | 0건 |
| 기대 사실 포함 | 29/29 | 28/29 |
| 평균 입력 토큰 | 6,641 | 5,857 |
| 비용 | $0.818721 | $0.746115 |

before의 위키 인용 누락 6문항(q01·q02·q03·q04·q25·q26)은 모두 after에서 통과했다. 반대로 **q06은 실제 답변 회귀**다. before는 일반 입고 검수의 2시간 기준을 답했지만 after는 반품 검수의 48시간 기준으로 답했다. 정답 위키가 검색 상위 8에서 사라진 회귀가 답변에 이어졌으며, 어휘 채널의 기존 약점과 연관됐을 가능성만으로 이번 회귀를 제외하지 않는다.

**사전 성공 기준을 충족했고, 사용자가 q06 회귀를 포함해 채택을 승인했다(2026-11-08).** 원문 상위 6 진입 질문 증가, 공식 통과율·recall 비감소, 위조 앵커 0건과 답변 통과 문항 비감소를 모두 만족했다. q06 회귀와 기대 사실 포함 감소는 남은 한계다. 동일 수집으로 재었지만 LLM 답변 변동은 남아 있어 한 번의 재생을 운영 효과로 일반화하지 않는다. after 전체 비용은 $0.764274, 첫 점검 문항은 $0.020520이었다.
